# 调试与性能分析 · 你 CS 教育的缺失学期 --- Debugging and Profiling · the missing semester of your cs education

# 调试与性能分析

编程中有一条黄金法则：代码不会做你期望它做的事情，而是会做你告诉它做的事情。弥合这种差距有时是一项相当艰巨的任务。在本讲座中，我们将介绍处理有错误且资源消耗大的代码的实用技术：调试与性能分析。

# 调试

## printf 调试与日志记录

> 最有效的调试工具仍然是仔细思考，并结合适当地放置打印语句

调试程序的第一种方法是围绕你发现问题的位置添加打印语句，并不断迭代，直到提取足够的信息来理解是什么导致了问题。

第二种方法是使用程序中的日志记录，而不是临时的打印语句。日志记录本质上是“更谨慎地打印”，通常通过一个包含对以下内容内置支持的日志记录框架来完成：

- 将日志（或日志的子集）定向到其他输出位置的能力；
- 设置严重程度级别（如 INFO、DEBUG、WARN、ERROR 等），并允许你根据这些级别过滤输出；
- 支持结构化日志记录与日志条目相关的数据，这样事后可以更轻松地提取这些数据。

日志语句通常在编程时主动添加，以便调试所需的数据已经存在！确实，一旦你通过打印语句找到并修复了问题，通常值得在移除这些打印语句之前将其转换为适当的日志语句。这样，如果将来出现类似的错误，你将无需修改代码即可获得所需的诊断信息。

›››注意 1›››

> **Third-party logs**: Many programs support the `-v` or `--verbose` flag to print more information when they run. This can be useful for discovering why a given command fails. Some even allow repeating the flag for more details. When debugging issues with services (databases, web servers, etc.), check their logs—often in `/var/log/` on Linux. Use `journalctl -u <service>` to view logs for systemd services. For third-party libraries, check if they support debug logging via environment variables or configuration.

## 调试器

打印调试在你知道该打印什么并且可以轻松修改和重新运行代码时效果很好。当不确定需要哪些信息、错误只在难以复现的情况下出现，或者修改和重启程序成本很高（如启动时间长、需要重建复杂状态等）时，调试器就变得非常有价值。

调试器是允许你在程序执行时与之交互的程序，它让你能够：

- 在到达某一行时停止执行。
- 逐条指令地单步执行。
- 在崩溃后检查变量的值。
- 在满足给定条件时暂停执行。
- 还有更多高级功能。

大多数编程语言都支持（或附带）某种形式的调试器。最通用的调试器是像 [gdb](https://www.gnu.org/software/gdb/)（GNU 调试器）和 [lldb](https://lldb.llvm.org/)（LLVM 调试器）这样的 **通用调试器**，它们可以调试任何原生二进制文件。许多语言也有与运行时更紧密集成的 特定语言调试器 （如 Python 的 pdb 或 Java 的 jdb）。

`gdb` 是 C、C++、Rust 以及其他编译型语言的实际标准调试器。它允许你探测几乎任何进程并获取其当前的机器状态：寄存器、堆栈、程序计数器等。

一些有用的 GDB 命令：

- `run` - 启动程序
- `b {function}` 或 `b {file}:{line}` - 设置断点
- `c` - 继续执行
- `step` / `next` / `finish` - 单步进入 / 单步跳过 / 单步跳出
- `p {variable}` - 打印变量的值
- `bt` - 显示调用栈
- `watch {expression}` - 当值变化时断点

›››注意 2›››

> Consider using GDB’s TUI mode (`gdb -tui` or press `Ctrl-x a` inside GDB) for a split-screen view showing source code alongside the command prompt.

### 记录-回放调试

最令人沮丧的某些错误是 *海森堡错误*：当你试图观察它们时，这些错误似乎会消失或改变行为。竞态条件、时序依赖性错误以及仅在特定系统条件下出现的错误都属于这一类别。传统调试方法在这种情况下往往无济于事，因为再次运行程序会产生不同的行为（例如，打印语句可能会使代码变慢到足以让竞态条件不再发生）。

**记录回放调试** 通过记录程序的执行并允许你按需多次确定性地回放它来解决这一问题。更棒的是，你可以 *逆向* 执行过程，以找到问题发生的确切位置。

[rr](https://rr-project.org/) 是一个强大的 Linux 工具，用于记录程序执行并允许具有完整调试功能的确定性重放。它与 GDB 配合使用，所以你已经熟悉这个界面。

基本用法：

```bash
# Record a program execution
rr record ./my_program

# Replay the recording (opens GDB)
rr replay
```

魔法发生在回放过程中。因为执行是确定的，你可以使用 **反向调试** 命令：

- `reverse-continue` (`rc`) - 向后运行直到遇到断点
- `reverse-step` (`rs`) - 向后单步执行
- `reverse-next` (`rn`) - 向后单步执行，跳过函数调用
- `reverse-finish` - 向后执行直到进入当前函数

这对于调试非常强大。假设你遇到了崩溃——你不需要猜测错误在哪里并设置断点，你可以：

1. 运行到崩溃处
2. 检查损坏的状态
3. 在损坏的变量上设置监视点
4. `reverse-continue` 以找到它被损坏的确切位置

**何时使用 rr：**

- 间歇性失败的不可靠测试
- 竞态条件和线程错误
- 难以复现的崩溃
- 任何你希望能够“回到过去”的 bug

›››注意 3›››

> Note: rr only works on Linux and requires hardware performance counters. It doesn’t work in VMs that don’t expose these counters, such as on most AWS EC2 instances, and it doesn’t support GPU access. For macOS, check out [Warpspeed](https://warpspeed.dev/).

> **rr 和并发**：由于 rr 以确定性方式记录执行，它会串行化线程调度。这意味着某些竞态条件如果依赖于特定时间可能不会在 rr 下显现。rr 仍然对调试竞态条件很有用——一旦你捕获了一次失败的运行，你就可以可靠地重放它——但你可能需要多次录制尝试来捕获间歇性错误。对于不涉及并发的错误，rr 效果最佳：你可以始终重现精确的执行，并使用反向调试来追踪损坏。

## 系统调用跟踪

有时你需要了解你的程序如何与操作系统交互。程序通过[系统调用](https://en.wikipedia.org/wiki/System_call)向内核请求服务——打开文件、分配内存、创建进程等。追踪这些调用可以揭示程序为何挂起、它试图访问哪些文件，或它花费时间等待的位置。

### strace (Linux) 和 dtruss (macOS)

[strace](https://www.man7.org/linux/man-pages/man1/strace.1.html) 可以让你观察到程序所进行的每一个系统调用：

```bash
# Trace all system calls
strace ./my_program

# Trace only file-related calls
strace -e trace=file ./my_program

# Follow child processes (important for programs that start other programs)
strace -f ./my_program

# Trace a running process
strace -p <PID>

# Show timing information
strace -T ./my_program
```

›››注意 4›››

> On macOS and BSD, use [dtruss](https://www.manpagez.com/man/1/dtruss/) (which wraps `dtrace`) for similar functionality:

> 若要深入了解 `strace`，可以查看朱莉娅·伊文斯编写的优秀 [strace 杂志](https://jvns.ca/strace-zine-unfolded.pdf)。

### bpftrace 和 eBPF

[eBPF](https://ebpf.io/)（扩展 Berkeley 数据包过滤器）是一种强大的 Linux 技术，允许在内核中运行沙盒程序。[bpftrace](https://github.com/iovisor/bpftrace) 为编写 eBPF 程序提供了高级语法。这些是在内核中运行的任意程序，因此具有巨大的表达能力（尽管其语法也有些笨拙的 awk 风格）。它们最常见的用途是调查被调用的系统调用，包括聚合（如计数或延迟统计）或内省（甚至基于系统调用参数进行过滤）。

```bash
# Trace file opens system-wide (prints immediately)
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s %s\n", comm, str(args->filename)); }'

# Count system calls by name (prints summary on Ctrl-C)
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_* { @[probe] = count(); }'
```

不过，你也可以使用像 [bcc](https://github.com/iovisor/bcc) 这样的工具链直接用 C 语言编写 eBPF 程序，它还提供了许多方便的工具，比如 `biosnoop` 用于打印磁盘操作的延迟分布，或 `opensnoop` 用于打印所有打开的文件。

虽然 `strace` 因为容易“快速上手”而有用，但当你需要更低的开销、想通过内核函数进行跟踪、需要进行任何类型的聚合时，应该使用 `bpftrace`。注意，`bpftrace` 必须以 `root` 身份运行，并且它通常监控整个内核，而不仅仅是特定进程。要针对特定程序，你可以通过命令名或 PID 进行过滤：

```bash
# Filter by command name (prints summary on Ctrl-C)
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_* /comm == "bash"/ { @[probe] = count(); }'

# Trace a specific command from startup using -c (cpid = child PID)
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_* /pid == cpid/ { @[probe] = count(); }' -c 'ls -la'
```

`-c` 标志运行指定的命令并将 `cpid` 设置为其 PID，这对于从程序启动时开始跟踪非常有用。当被跟踪的命令退出时，bpftrace 会打印聚合的结果。

### 网络调试

对于网络问题，[tcpdump](https://www.man7.org/linux/man-pages/man1/tcpdump.1.html) 和 [Wireshark](https://www.wireshark.org/) 可以让你捕获和分析网络数据包：

```bash
# Capture packets on port 80
sudo tcpdump -i any port 80

# Capture and save to file for Wireshark analysis
sudo tcpdump -i any -w capture.pcap
```

对于 HTTPS 流量，加密使得 tcpdump 变得不太有用。像 [mitmproxy](https://mitmproxy.org/) 这样的工具可以作为拦截代理来检查加密流量。浏览器开发者工具（网络标签页）通常是调试 Web 应用程序 HTTPS 请求的最简单方法——它们显示解密的请求/响应数据、标头和时间。

## 内存调试

内存错误——缓冲区溢出、使用后释放、内存泄漏——是最危险且最难调试的问题之一。它们通常不会立即崩溃，但会以某种方式损坏内存，导致后期出现问题。

### 内存清理工具

一种查找内存错误的方法是使用 **sanitizers**，这是一种编译器功能，它会在运行时检测代码中的错误。例如，广泛使用的 **AddressSanitizer (ASan)** 可以检测：

- 缓冲区溢出（栈、堆和全局）
- 使用后释放
- 返回后使用
- 内存泄漏

```bash
# Compile with AddressSanitizer
gcc -fsanitize=address -g program.c -o program
./program
```

存在多种有用的清理工具：

- **ThreadSanitizer (TSan)**: 检测多线程代码中的数据竞争 (`-fsanitize=thread`)
- **MemorySanitizer (MSan)**: 检测未初始化内存的读取 (`-fsanitize=memory`)
- **UndefinedBehaviorSanitizer (UBSan)**: 检测整数溢出等未定义行为 (`-fsanitize=undefined`)

Sanitizers 需要重新编译，但足够快，可以在 CI 管道和常规开发中使用。

### Valgrind：当你无法重新编译时

[Valgrind](https://valgrind.org/) 则在类似虚拟机的环境中运行你的程序以检测内存错误。它比清理器慢，但不需要重新编译：

```bash
valgrind --leak-check=full ./my_program
```

当你没有源代码时使用 Valgrind：

- 你无法获得源代码
- 你不能重新编译（第三方库）
- 你需要特定的工具，而这些工具不可作为清理器使用

Valgrind 实际上是一个非常强大的受控执行环境，稍后当我们进入性能分析时，我们会看到更多关于它的内容！

## AI 辅助调试

大型语言模型已成为令人惊讶的有用调试助手。它们在传统工具互补的某些调试任务中表现出色。

**LLMs 的优势：**

- **解释晦涩的错误信息**：编译器错误，尤其是来自 C++模板或 Rust 的借用检查器的错误，可能非常晦涩难懂。LLMs 可以将它们翻译成普通英语并建议修复方法。
- **跨越语言和抽象边界**：如果你正在调试一个涉及多种语言的问题（比如，一个 C 库中的错误通过 Python 绑定表现出来），LLMs 可以帮助你导航不同的层次。它们特别擅长理解 FFI 边界、构建系统问题和跨语言调试（例如，我的程序出错，但我认为是因为我的某个依赖项中的错误）。
- **将症状与根本原因关联起来**：“我的程序运行正常但使用了比预期多 10 倍的内存”这类模糊的症状，LLMs 可以帮助调查，并指出可能的根本原因以及需要查找的内容。
- **分析崩溃转储和堆栈跟踪**：粘贴一个堆栈跟踪并询问可能的原因。

›››注意 5›››

> **Note on debug symbols**: For meaningful stack traces and debugging, ensure your binaries (and any linked libraries) are compiled with debug symbols (`-g` flag). Debug information is typically stored in DWARF format. Additionally, compiling with frame pointers (`-fno-omit-frame-pointer`) makes stack traces more reliable, especially for profiling tools. Without these, stack traces may show only memory addresses or be incomplete. This matters more for natively compiled programs (C++, Rust) than Python or Java.

**需要注意的限制：**

- LLMs 可能会编造听起来合理但错误的解释
- 它们可能会提出掩盖错误而非修复错误的解决方案
- 始终使用实际调试工具验证建议
- 它们最适合作为理解代码的补充，而非替代

# 分析

即使你的代码在功能上表现符合预期，但如果它消耗了所有你的 CPU 或内存，那可能还不够好。算法课程通常教授大 O 符号，但并不教如何找到程序中的热点。由于过早优化是万恶之源，你应该学习使用分析器和监控工具。它们将帮助你了解程序中哪些部分消耗了最多时间和/或资源，以便你可以专注于优化这些部分。

## 计时

衡量性能最简单的方法是计时。在许多情况下，只需打印代码在两个点之间所花费的时间就足够了。

然而，墙上时钟时间可能会具有误导性，因为你的计算机可能同时运行其他进程或等待事件发生。`time` 命令区分*真实*、*用户*和*系统*时间：

- **真实** - 从开始到结束的墙上时钟时间，包括等待所花费的时间
- **用户** - CPU 运行用户代码所花费的时间
- **系统** - CPU 运行内核代码所花费的时间

```bash
$ time curl https://missing.csail.mit.edu &> /dev/null
real	0m0.272s
user	0m0.079s
sys	    0m0.028s
```

在这里，请求花费了将近 300 毫秒（真实时间），但只有 107 毫秒的 CPU 时间（用户+系统）。其余时间是在等待网络。

## 资源监控

分析程序性能的第一步有时是了解其实际资源消耗情况。当程序资源受限时，它们往往运行缓慢。

- **通用监控**: [htop](https://htop.dev/) 是 `top` 的改进版本，提供当前运行进程的各种统计数据。有用快捷键：`<F6>` 排序进程，`t` 显示树形层级，`h` 切换线程。还有 [btop](https://github.com/aristocratos/btop) 可以监控更多内容。
- **输入输出操作**: [iotop](https://www.man7.org/linux/man-pages/man8/iotop.8.html) 显示实时输入输出使用信息。
- **内存使用**: [free](https://www.man7.org/linux/man-pages/man1/free.1.html) 显示总空闲和已用内存。
- **打开文件**: [lsof](https://www.man7.org/linux/man-pages/man8/lsof.8.html) 列出进程打开的文件信息。可用于检查哪个进程打开了特定文件。
- **网络连接**: [ss](https://www.man7.org/linux/man-pages/man8/ss.8.html) 允许你监控网络连接。一个常见用例是找出使用特定端口的进程：`ss -tlnp | grep :8080`。
- **网络使用情况**: [nethogs](https://github.com/raboof/nethogs) 和 [iftop](https://pdw.ex-parrot.com/iftop/) 是用于按进程监控网络使用情况的优秀交互式 CLI 工具。

## 可视化性能数据

人类在图形中识别模式的速度远快于在数字表格中。在分析性能时，将数据绘制成图表往往能揭示原始数字中无法显现的趋势、峰值和异常情况。

**使数据可绘图**: 在添加用于调试的打印或日志语句时，考虑将输出格式化为稍后可以轻松绘图。CSV 格式的简单时间戳和值（`1705012345,42.5`）比一段散文更容易绘图。JSON 结构的日志也可以通过少量工作解析并绘图。换句话说，以整洁的方式记录你的数据 [in a tidy way](https://vita.had.co.nz/papers/tidy-data.pdf)。

**使用 gnuplot 快速绘图**: 对于简单的命令行绘图，[gnuplot](http://www.gnuplot.info/) 可以直接从数据文件生成图表：

```bash
# Plot a simple CSV with timestamp,value
gnuplot -e "set datafile separator ','; plot 'latency.csv' using 1:2 with lines"
```

**使用 matplotlib 和 ggplot2 进行迭代探索**：为了进行更深入的分析，Python 的 [matplotlib](https://matplotlib.org/) 和 R 的 [ggplot2](https://ggplot2.tidyverse.org/) 能够支持迭代探索。与一次性绘图不同，这些工具让你可以快速地对数据进行切片和转换，以验证假设。ggplot2 的分组图特别强大——你可以通过类别将单个数据集拆分到多个子图上（例如，按端点或一天中的时间分组展示请求延迟），从而揭示原本隐藏的模式。

**示例用例：**

- 绘制请求延迟随时间的变化可以揭示周期性减速（垃圾回收、定时任务、流量模式），而原始百分位数会掩盖这些问题
- 可视化增长数据结构的插入时间可以暴露算法复杂性问题——当支持数组大小翻倍时，向量插入的图表将显示出特征性尖峰
- 通过不同维度（请求类型、用户群体、服务器）对指标进行细分，通常会发现所谓的“全局问题”实际上仅限于某一特定类别

## CPU 分析器

大多数情况下，当人们提到 *分析器* 时，指的是 *CPU 分析器*。主要有两种类型：

- **跟踪分析器** 记录你的程序所进行的每个函数调用
- **采样分析器** 定期（通常每毫秒）探测你的程序并记录程序的堆栈

采样分析器具有较低的额外开销，通常更受生产环境的使用青睐。

### perf: 采样分析器

[perf](https://www.man7.org/linux/man-pages/man1/perf.1.html) 是标准的 Linux 分析器。它可以在不重新编译的情况下分析任何程序：

`perf stat` 可以让你快速了解时间花在哪里：

```bash
$ perf stat ./slow_program

 Performance counter stats for './slow_program':

         3,210.45 msec task-clock                #    0.998 CPUs utilized
               12      context-switches          #    3.738 /sec
                0      cpu-migrations            #    0.000 /sec
              156      page-faults               #   48.587 /sec
   12,345,678,901      cycles                    #    3.845 GHz
    9,876,543,210      instructions              #    0.80  insn per cycle
    1,234,567,890      branches                  #  384.532 M/sec
       12,345,678      branch-misses             #    1.00% of all branches
```

现实世界程序的剖析器输出将包含大量信息。人类是视觉生物，对于阅读大量数字相当糟糕。[火焰图](https://www.brendangregg.com/flamegraphs.html)是一种可视化方式，使剖析数据更容易理解。

火焰图在 Y 轴上显示函数调用的层次结构，在 X 轴上按时间比例显示。它们是交互式的——你可以点击放大程序的特定部分。

[Link](https://www.brendangregg.com/FlameGraphs/cpu-bash-flamegraph.svg)

要从 `perf` 数据生成火焰图：

```bash
# Record profile
perf record -g ./my_program

# Generate flame graph (requires flamegraph scripts)
perf script | stackcollapse-perf.pl | flamegraph.pl > flamegraph.svg
```

›››注意 7›››

> Consider using [Speedscope](https://www.speedscope.app/) for an interactive web-based flame graph viewer, or [Perfetto](https://perfetto.dev/) for comprehensive system-level analysis.

### Valgrind 的 Callgrind：跟踪分析器

[callgrind](https://valgrind.org/docs/manual/cl-manual.html) 是一个剖析工具，记录程序的调用历史和指令计数。与采样剖析器不同，它提供精确的调用计数，并可以显示调用者和被调用者之间的关系：

```bash
# Run with callgrind
valgrind --tool=callgrind ./my_program

# Analyze with callgrind_annotate (text) or kcachegrind (GUI)
callgrind_annotate callgrind.out.<pid>
kcachegrind callgrind.out.<pid>
```

Callgrind 比采样剖析器慢，但提供精确的调用计数，并且如果需要这些信息，可以选择性地模拟缓存行为（使用 `--cache-sim=yes`）。

›››note 8›››

> If you’re using a particular language, there may be more specialized profilers. For example, Python has [cProfile](https://docs.python.org/3/library/profile.html) and [py-spy](https://github.com/benfred/py-spy), Go has [go tool pprof](https://pkg.go.dev/cmd/pprof), and Rust has [cargo-flamegraph](https://github.com/flamegraph-rs/flamegraph) (which actually works for any compiled program!).

## 内存分析器

内存分析器帮助你了解程序随时间如何使用内存，并找出内存泄漏。

### Valgrind 的 Massif

[massif](https://valgrind.org/docs/manual/ms-manual.html) 分析堆内存使用情况：

```bash
valgrind --tool=massif ./my_program
ms_print massif.out.<pid>
```

这显示了随时间变化的堆内存使用情况，有助于识别内存泄漏和过度分配。

›››注意 9›››

> For Python, [memory-profiler](https://pypi.org/project/memory-profiler/) provides line-by-line memory usage information.

# 练习

## 调试

1. **调试排序算法**: 以下伪代码实现了归并排序但存在一个错误。用你选择的语言实现它，然后使用调试器（gdb、lldb、pdb 或你 IDE 的调试器）找到并修复错误。 ```plaintext
   function merge_sort(arr):
    if length(arr) <= 1:
        return arr
    mid = length(arr) / 2
    left = merge_sort(arr[0..mid])
    right = merge_sort(arr[mid..end])
    return merge(left, right)

function merge(left, right):
    result = []
    i = 0, j = 0
    while i < length(left) AND j < length(right):
        if left[i] <= right[j]:
            append result, left[i]
            i = i + 1
        else:
            append result, right[i]
            j = j + 1
    append remaining elements from left and right
    return result
``` 测试向量：`merge_sort([3, 1, 4, 1, 5, 9, 2, 6])` 应返回 `[1, 1, 2, 3, 4, 5, 6, 9]`。使用断点并逐步调试合并函数，以找到错误元素被选择的位置。
2. 安装 [rr](https://rr-project.org/) 并使用逆向调试来查找损坏的 bug。将此程序保存为 `corruption.c`： ```c
#include <stdio.h>

typedef struct {
    int id;
    int scores[3];
} Student;

Student students[2];

void init() {
    students[0].id = 1001;
    students[0].scores[0] = 85;
    students[0].scores[1] = 92;
    students[0].scores[2] = 78;

    students[1].id = 1002;
    students[1].scores[0] = 90;
    students[1].scores[1] = 88;
    students[1].scores[2] = 95;
}

void curve_scores(int student_idx, int curve) {
    for (int i = 0; i < 4; i++) {
        students[student_idx].scores[i] += curve;
    }
}

int main() {
    init();
    printf("=== Initial state ===\n");
    printf("Student 0: id=%d\n", students[0].id);
    printf("Student 1: id=%d\n", students[1].id);

    curve_scores(0, 5);
    
    printf("\n=== After curving ===\n");
    printf("Student 0: id=%d\n", students[0].id);
    printf("Student 1: id=%d\n", students[1].id);
    
    if (students[1].id != 1002) {
        printf("\nERROR: Student 1's ID was corrupted! Expected 1002, got %d\n",
               students[1].id);
        return 1;
    }
    return 0;
}
``` 使用 `gcc -g corruption.c -o corruption` 编译并运行它。学生 1 的 ID 被破坏了，但破坏发生在只访问学生 0 的函数中。使用 `rr record ./corruption` 和 `rr replay` 找到罪魁祸首。在 `students[1].id` 上设置一个断点，并在破坏后使用 `reverse-continue` 找到具体是哪一行代码覆盖了它。
3. 使用 AddressSanitizer 调试内存错误。将以下内容保存为 `uaf.c`： ```c
#include <stdlib.h>
#include <string.h>
#include <stdio.h>

int main() {
    char *greeting = malloc(32);
    strcpy(greeting, "Hello, world!");
    printf("%s\n", greeting);

    free(greeting);
    
    greeting[0] = 'J';
    printf("%s\n", greeting);
    
    return 0;
}
``` 首先在没有启用 sanitizers 的情况下编译并运行：`gcc uaf.c -o uaf && ./uaf`。它可能看起来可以工作。现在使用 AddressSanitizer 编译：`gcc -fsanitize=address -g uaf.c -o uaf && ./uaf`。阅读错误报告。ASan 发现了什么 bug？修复它识别出的问题。
4. 使用 `strace`（Linux）或 `dtruss`（macOS）来追踪命令如 `ls -l` 所做的系统调用。它在调用哪些系统调用？尝试追踪一个更复杂的程序，看看它打开了哪些文件。
5. 使用 LLM 来帮助调试一个神秘的错误消息。尝试复制一个编译器错误（尤其是来自 C++ 模板或 Rust 的错误），并请求解释和修复。尝试将 `strace` 或地址清理器的部分输出放入其中。

## 分析

1. 使用 `perf stat` 获取您选择的程序的基本性能统计数据。不同的计数器代表什么含义？
2. 使用 `perf record` 进行分析。将结果保存为 `slow.c`： ```c
#include <math.h>
#include <stdio.h>

double slow_computation(int n) {
    double result = 0;
    for (int i = 0; i < n; i++) {
        for (int j = 0; j < 1000; j++) {
            result += sin(i * j) * cos(i + j);
        }
    }
    return result;
}

int main() {
    double r = 0;
    for (int i = 0; i < 100; i++) {
        r += slow_computation(1000);
    }
    printf("Result: %f\n", r);
    return 0;
}
``` 编译时包含调试符号：`gcc -g -O2 slow.c -o slow -lm`。运行 `perf record -g ./slow`，然后使用 `perf report` 查看时间消耗情况。尝试使用火焰图脚本生成火焰图。
3. 使用 `hyperfine` 对同一任务的两个不同实现进行基准测试（例如，`find` 对比 `fd`，`grep` 对比 `ripgrep`，或你自己的代码的两个版本）。
4. 使用 `htop` 在运行资源密集型程序时监控系统。尝试使用 `taskset` 限制进程可使用的 CPU：`taskset --cpu-list 0,2 stress -c 3`。为什么 `stress` 没有使用三个 CPU？
5. 常见问题是，你想监听的端口已被其他进程占用。学习如何发现该进程：首先执行 `python -m http.server 4444` 在 4444 端口启动一个简单的 Web 服务器。在另一个终端运行 `ss -tlnp | grep 4444` 找到该进程。使用 `kill <PID>` 终止它。
