# Debugging and Profiling调试与性能分析

A golden rule in programming is that code does not do what you expect it to do, but what you tell it to do. Bridging that gap can sometimes be a quite difficult feat. In this lecture we are going to cover useful techniques for dealing with buggy and resource hungry code: debugging and profiling.编程中有一条黄金法则：代码不会做你期望它做的事情，而是会做你告诉它做的事情。弥合这种差距有时是一项相当艰巨的任务。在本讲座中，我们将介绍处理有错误且资源消耗大的代码的实用技术：调试与性能分析。

# Debugging调试

## Printf Debugging and Loggingprintf 调试与日志记录

> The most effective debugging tool is still careful thought, coupled with judiciously placed print statements最有效的调试工具仍然是仔细思考，并结合适当地放置打印语句

A first approach to debug a program is to add print statements around where you have detected the problem, and keep iterating until you have extracted enough information to understand what is responsible for the issue.调试程序的第一种方法是围绕你发现问题的位置添加打印语句，并不断迭代，直到提取足够的信息来理解是什么导致了问题。

A second approach is to use logging in your program, instead of ad hoc print statements. Logging is essentially “printing with more care”, and is usually done through a logging framework that includes built-in support for things like:第二种方法是使用程序中的日志记录，而不是临时的打印语句。日志记录本质上是“更谨慎地打印”，通常通过一个包含对以下内容内置支持的日志记录框架来完成：

- the ability to direct the logs (or subsets of the logs) to other output locations;将日志（或日志的子集）定向到其他输出位置的能力；
- setting severity levels (such as INFO, DEBUG, WARN, ERROR, etc.) and allow you to filter the output according to those; and设置严重程度级别（如 INFO、DEBUG、WARN、ERROR 等），并允许你根据这些级别过滤输出；
- support for structured logging of data related to the log entries, which can then be extracted more easily after the fact.支持结构化日志记录与日志条目相关的数据，这样事后可以更轻松地提取这些数据。

Logging statements you’ll also usually proactively put in while programming so that the data you need to debug may already be there! And indeed, once you’ve found and fixed a problem using print statements, it’s often worthwhile to convert those prints into proper log statements before removing them. This way, if similar bugs occur in the future, you’ll already have the diagnostic information you need without modifying the code.日志语句通常在编程时主动添加，以便调试所需的数据已经存在！确实，一旦你通过打印语句找到并修复了问题，通常值得在移除这些打印语句之前将其转换为适当的日志语句。这样，如果将来出现类似的错误，你将无需修改代码即可获得所需的诊断信息。

›››note 1注意 1›››

> **Third-party logs**: Many programs support the `-v` or `--verbose` flag to print more information when they run. This can be useful for discovering why a given command fails. Some even allow repeating the flag for more details. When debugging issues with services (databases, web servers, etc.), check their logs—often in `/var/log/` on Linux. Use `journalctl -u <service>` to view logs for systemd services. For third-party libraries, check if they support debug logging via environment variables or configuration.

## Debuggers调试器

Print debugging works well when you know what to print and can easily modify and re-run your code. Debuggers become valuable when you’re not sure what information you need, when the bug only manifests in hard-to-reproduce conditions, or when modifying and restarting the program is expensive (long startup times, complex state to recreate, etc.).打印调试在你知道该打印什么并且可以轻松修改和重新运行代码时效果很好。当不确定需要哪些信息、错误只在难以复现的情况下出现，或者修改和重启程序成本很高（如启动时间长、需要重建复杂状态等）时，调试器就变得非常有价值。

Debuggers are programs that let you interact with the execution of a program as it happens, allowing you to:调试器是允许你在程序执行时与之交互的程序，它让你能够：

- Halt execution when it reaches a certain line.在到达某一行时停止执行。
- Step through one instruction at a time.逐条指令地单步执行。
- Inspect values of variables after a crash.在崩溃后检查变量的值。
- Conditionally halt execution when a given condition is met.在满足给定条件时暂停执行。
- And many more advanced features.还有更多高级功能。

Most programming languages support (or come with) some form of debugger. The most versatile are **general-purpose debuggers** like [gdb](https://www.gnu.org/software/gdb/) (GNU Debugger) and [lldb](https://lldb.llvm.org/) (LLVM Debugger), which can debug any native binary. Many languages also have **language-specific debuggers** that integrate more tightly with the runtime (like Python’s pdb or Java’s jdb).大多数编程语言都支持（或附带）某种形式的调试器。最通用的调试器是通用调试器，如 `gdb` （GNU 调试器）和 `lldb` （LLVM 调试器），它们可以调试任何原生二进制文件。许多语言也有特定于语言的调试器，这些调试器与运行时更紧密集成（例如 Python 的 pdb 或 Java 的 jdb）。

`gdb` is the de-facto standard debugger for C, C++, Rust, and other compiled languages. It lets you probe pretty much any process and get its current machine state: registers, stack, program counter, and more.`gdb` 是 C、C++、Rust 和其他编译型语言的事实标准调试器。它允许你探测几乎任何进程并获取其当前机器状态：寄存器、堆栈、程序计数器等。

Some useful GDB commands:一些有用的 GDB 命令：

- `run` - Start the program`run` - 启动程序
- `b {function}` or `b {file}:{line}` - Set a breakpoint`b {function}` 或 `b {file}:{line}` - 设置断点
- `c` - Continue execution`c` - 继续执行
- `step` / `next` / `finish` - Step in / step over / step out`step` / `next` / `finish` - 单步进入 / 单步跳过 / 单步跳出
- `p {variable}` - Print value of variable`p {variable}` - 打印变量值
- `bt` - Show backtrace (call stack)`bt` - 显示调用栈
- `watch {expression}` - Break when the value changes`watch {expression}` - 当值变化时断点

›››note 2注意 2›››

> Consider using GDB’s TUI mode (`gdb -tui` or press `Ctrl-x a` inside GDB) for a split-screen view showing source code alongside the command prompt.

### Record-Replay Debugging记录-回放调试

Some of the most frustrating bugs are *Heisenbugs*: bugs that seem to disappear or change behavior when you try to observe them. Race conditions, timing-dependent bugs, and issues that only appear under certain system conditions fall into this category. Traditional debugging is often useless here because running the program again produces different behavior (e.g., print statements may slow down the code sufficiently that the race no longer happens).有些最令人沮丧的 bug 是海森堡 bug：当你试图观察它们时，这些 bug 似乎会消失或改变行为。竞态条件、时间依赖性 bug 以及仅在特定系统条件下出现的问题都属于这一类。传统调试在这里往往无效，因为重新运行程序会产生不同的行为（例如，打印语句可能会使代码变慢到足以让竞态条件不再发生）。

**Record-replay debugging** solves this by recording a program’s execution and allowing you to replay it deterministically as many times as you need. Even better, you can *reverse* through the execution to find exactly where things went wrong.记录回放调试通过记录程序的执行并允许你根据需要多次确定性地回放它来解决这一问题。更棒的是，你可以通过执行过程来回溯，以找到问题发生的确切位置。

[rr](https://rr-project.org/) is a powerful tool for Linux that records program execution and allows deterministic replay with full debugging capabilities. It works with GDB, so you already know the interface.rr 是一个强大的 Linux 工具，用于记录程序执行并允许具有完整调试功能的确定性重放。它与 GDB 配合使用，所以你已经熟悉其界面。

Basic usage:基本用法：

```bash
# Record a program execution
rr record ./my_program

# Replay the recording (opens GDB)
rr replay
```

The magic happens during replay. Because the execution is deterministic, you can use **reverse debugging** commands:魔法发生在重放过程中。由于执行是确定性的，你可以使用反向调试命令：

- `reverse-continue` (`rc`) - Run backwards until hitting a breakpoint`reverse-continue` ( `rc` ) - 向后运行直到命中断点
- `reverse-step` (`rs`) - Step backwards one line`reverse-step` ( `rs` ) - 向后一步一行
- `reverse-next` (`rn`) - Step backwards, skipping function calls`reverse-next` ( `rn` ) - 向后一步，跳过函数调用
- `reverse-finish` - Run backwards until entering the current function`reverse-finish` - 向后运行直到进入当前函数

This is incredibly powerful for debugging. Say you have a crash—instead of guessing where the bug is and setting breakpoints, you can:这对于调试非常强大。假设你遇到了崩溃——你不需要猜测错误在哪里并设置断点，你可以：

1. Run to the crash运行到崩溃处
2. Inspect the corrupted state检查损坏的状态
3. Set a watchpoint on the corrupted variable在损坏的变量上设置监视点
4. `reverse-continue` to find exactly where it was corrupted`reverse-continue` 找到它被损坏的确切位置

**When to use rr:何时使用 rr：**

- Flaky tests that fail intermittently间歇性失败的不可靠测试
- Race conditions and threading bugs竞态条件和线程错误
- Crashes that are hard to reproduce难以复现的崩溃
- Any bug where you wish you could “go back in time”任何你希望能够“回到过去”的 bug

›››note 3注意 3›››

> Note: rr only works on Linux and requires hardware performance counters. It doesn’t work in VMs that don’t expose these counters, such as on most AWS EC2 instances, and it doesn’t support GPU access. For macOS, check out [Warpspeed](https://warpspeed.dev/).

> **rr and concurrency**: Because rr records execution deterministically, it serializes thread scheduling. This means some race conditions may not manifest under rr if they depend on specific timing. rr is still useful for debugging races—once you capture a failing run, you can replay it reliably—but you may need multiple recording attempts to catch an intermittent bug. For bugs that don’t involve concurrency, rr shines brightest: you can always reproduce the exact execution and use reverse debugging to hunt down corruption.rr 和并发：因为 rr 以确定性方式记录执行，它会序列化线程调度。这意味着如果某些竞态条件依赖于特定的时间，它们在 rr 下可能不会显现。rr 仍然适用于调试竞态条件——一旦捕获到一个失败的运行，你可以可靠地重放它——但你可能需要多次录制尝试来捕获间歇性错误。对于不涉及并发的错误，rr 表现最为出色：你可以始终重现精确的执行，并使用反向调试来追踪损坏。

## System Call Tracing系统调用跟踪

Sometimes you need to understand how your program interacts with the operating system. Programs make [system calls](https://en.wikipedia.org/wiki/System_call) to request services from the kernel—opening files, allocating memory, creating processes, and more. Tracing these calls can reveal why a program is hanging, what files it’s trying to access, or where it’s spending time waiting.有时你需要了解你的程序如何与操作系统交互。程序通过系统调用请求内核的服务——打开文件、分配内存、创建进程等。追踪这些调用可以揭示程序为何挂起、它试图访问哪些文件，或它花费时间等待的位置。

### strace (Linux) and dtruss (macOS)strace (Linux) 和 dtruss (macOS)

[strace](https://www.man7.org/linux/man-pages/man1/strace.1.html) lets you observe every system call a program makes:`strace` 允许你观察程序所进行的每一个系统调用：

```bash
# Trace all system calls
strace ./my_program

# Trace only file-related calls
strace -e trace=file ./my_program

# Follow child processes (important for programs that start other programs)
strace -f ./my_program

# Trace a running process
strace -p <PID>

# Show timing information
strace -T ./my_program
```

›››note 4注意 4›››

> On macOS and BSD, use [dtruss](https://www.manpagez.com/man/1/dtruss/) (which wraps `dtrace`) for similar functionality:

> For deeper dives into `strace`, check out Julia Evans’ excellent [strace zine](https://jvns.ca/strace-zine-unfolded.pdf).若想深入了解 `strace` ，可以查看 Julia Evans 的优秀 strace 杂志。

### bpftrace and eBPFbpftrace 和 eBPF

[eBPF](https://ebpf.io/) (extended Berkeley Packet Filter) is a powerful Linux technology that allows running sandboxed programs in the kernel. [bpftrace](https://github.com/iovisor/bpftrace) provides a high-level syntax for writing eBPF programs. These are arbitrary programs running in the kernel, and thus have huge expressive power (though also a somewhat clumsy awk-like syntax). The most common use-case for them is to investigate what system calls are being invoked, including aggregations (like counts or latency statistics) or introspecting (or even filtering on) system call arguments.eBPF（扩展伯克利数据包过滤器）是一项强大的 Linux 技术，允许在内核中运行沙盒程序。 `bpftrace` 提供了一种高级语法来编写 eBPF 程序。这些是在内核中运行的任意程序，因此具有巨大的表达能力（尽管其语法也有些笨拙的 awk 风格）。它们最常见的用途是调查被调用的系统调用，包括聚合（如计数或延迟统计）或内省（甚至过滤）系统调用参数。

```bash
# Trace file opens system-wide (prints immediately)
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s %s\n", comm, str(args->filename)); }'

# Count system calls by name (prints summary on Ctrl-C)
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_* { @[probe] = count(); }'
```

However, you can also write eBPF programs directly in C using a toolchain like [bcc](https://github.com/iovisor/bcc), which also ships with [many handy tools](https://www.brendangregg.com/blog/2015-09-22/bcc-linux-4.3-tracing.html) like `biosnoop` for printing latency distributions for disk operations or `opensnoop` for printing all open files.然而，你也可以使用像 `bcc` 这样的工具链直接用 C 语言编写 eBPF 程序，该工具链还附带了许多实用工具，例如 `biosnoop` 用于打印磁盘操作的延迟分布，或 `opensnoop` 用于打印所有打开的文件。

Where `strace` is useful because it’s easy to “just get up and running”, `bpftrace` is what you should reach for when you need lower overhead, want to trace through kernel functions, need to do any kind of aggregation, etc. Note that `bpftrace` has to run as `root` though, and that it generally monitors the entire kernel, not just a particular process. To target a specific program, you can filter by command name or PID:`strace` 之所以有用，是因为它容易“快速启动”，而 `bpftrace` 则是在你需要更低开销、想要跟踪内核函数、需要执行任何类型的聚合等情况时应该选择的目标。请注意， `bpftrace` 必须以 `root` 的形式运行，而且它通常监控整个内核，而不仅仅是特定的进程。要针对特定程序，你可以通过命令名或 PID 进行过滤：

```bash
# Filter by command name (prints summary on Ctrl-C)
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_* /comm == "bash"/ { @[probe] = count(); }'

# Trace a specific command from startup using -c (cpid = child PID)
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_* /pid == cpid/ { @[probe] = count(); }' -c 'ls -la'
```

The `-c` flag runs the specified command and sets `cpid` to its PID, which is useful for tracing a program from the moment it starts. When the traced command exits, bpftrace prints the aggregated results.`-c` 标志运行指定的命令，并将 `cpid` 设置为其进程 ID，这对于从程序启动时开始跟踪程序非常有用。当被跟踪的命令退出时，bpftrace 会打印聚合的结果。

### Network Debugging网络调试

For network issues, [tcpdump](https://www.man7.org/linux/man-pages/man1/tcpdump.1.html) and [Wireshark](https://www.wireshark.org/) let you capture and analyze network packets:对于网络问题， `tcpdump` 和 Wireshark 可以让你捕获和分析网络数据包：

```bash
# Capture packets on port 80
sudo tcpdump -i any port 80

# Capture and save to file for Wireshark analysis
sudo tcpdump -i any -w capture.pcap
```

For HTTPS traffic, the encryption makes tcpdump less useful. Tools like [mitmproxy](https://mitmproxy.org/) can act as an intercepting proxy to inspect encrypted traffic. Browser developer tools (Network tab) are often the easiest way to debug HTTPS requests from web applications—they show decrypted request/response data, headers, and timing.对于 HTTPS 流量，加密使得 tcpdump 不太有用。像 mitmproxy 这样的工具可以作为拦截代理来检查加密流量。浏览器开发者工具（网络标签）通常是调试 Web 应用程序 HTTPS 请求的最简单方法——它们显示解密的请求/响应数据、标头和时间。

## Memory Debugging内存调试

Memory bugs—buffer overflows, use-after-free, memory leaks—are among the most dangerous and difficult to debug. They often don’t crash immediately but corrupt memory in ways that cause problems much later.内存错误——缓冲区溢出、使用后释放、内存泄漏——是最危险且最难调试的问题之一。它们通常不会立即崩溃，但会以某种方式损坏内存，导致后期出现问题。

### Sanitizers内存清理工具

One approach to finding memory bugs is to use **sanitizers**, which are compiler features that instrument your code to detect errors at runtime. For example, the widely used **AddressSanitizer (ASan)** detects:查找内存错误的一种方法是使用内存清理工具，这些是编译器功能，用于在运行时检测代码中的错误。例如，广泛使用的 AddressSanitizer (ASan) 可以检测：

- Buffer overflows (stack, heap, and global)缓冲区溢出（栈、堆和全局）
- Use-after-free使用后释放
- Use-after-return返回后使用
- Memory leaks内存泄漏

```bash
# Compile with AddressSanitizer
gcc -fsanitize=address -g program.c -o program
./program
```

There are a variety of useful sanitizers:存在多种有用的清理工具：

- **ThreadSanitizer (TSan)**: Detects data races in multithreaded code (`-fsanitize=thread`)ThreadSanitizer (TSan): 检测多线程代码中的数据竞争 ( `-fsanitize=thread` )
- **MemorySanitizer (MSan)**: Detects reads of uninitialized memory (`-fsanitize=memory`)MemorySanitizer (MSan): 检测未初始化内存的读取 ( `-fsanitize=memory` )
- **UndefinedBehaviorSanitizer (UBSan)**: Detects undefined behavior like integer overflow (`-fsanitize=undefined`)UndefinedBehaviorSanitizer (UBSan): 检测整数溢出等未定义行为 ( `-fsanitize=undefined` )

Sanitizers require recompilation but are fast enough to use in CI pipelines and during regular development.Sanitizers 需要重新编译，但足够快，可以在 CI 管道和常规开发中使用。

### Valgrind: When You Can’t RecompileValgrind：当你无法重新编译时

[Valgrind](https://valgrind.org/) instead runs your program in something akin to a virtual machine to detect memory errors. It’s slower than sanitizers but doesn’t require recompilation:Valgrind 会运行你的程序在一个类似于虚拟机的环境中来检测内存错误。它比清理器慢，但不需要重新编译：

```bash
valgrind --leak-check=full ./my_program
```

Use Valgrind when:当你没有源代码时使用 Valgrind：

- You don’t have source code你无法获得源代码
- You can’t recompile (third-party libraries)你不能重新编译（第三方库）
- You need specific tools not available as sanitizers你需要特定的工具，而这些工具不可作为清理器使用

Valgrind is actually a really powerful controlled execution environment, and we’ll see more of it later when we get to profiling!Valgrind 实际上是一个非常强大的受控执行环境，稍后当我们进入性能分析时，我们会看到更多关于它的内容！

## AI for DebuggingAI 辅助调试

Large language models have become surprisingly useful debugging assistants. They excel at certain debugging tasks that complement traditional tools.大型语言模型已成为令人惊讶的有用调试助手。它们在传统工具互补的某些调试任务中表现出色。

**Where LLMs shine:LLMs 的优势：**

- **Explaining cryptic error messages**: Compiler errors, especially from C++ templates or Rust’s borrow checker, can be notoriously cryptic. LLMs can translate them into plain English and suggest fixes.解释晦涩的错误信息：编译器错误，尤其是来自 C++ 模板或 Rust 借用检查器的错误，可能非常晦涩。LLMs 可以将它们翻译成 plain English 并提出解决方案。
- **Traversing language and abstraction boundaries**: If you’re debugging a problem that spans multiple languages (say, a bug in a C library that manifests through a Python binding), LLMs can help navigate the different layers. They’re particularly good at understanding FFI boundaries, build system issues, and cross-language debugging (e.g., my program errors, but I believe it is because of a bug in one of my dependencies).跨越语言和抽象边界：如果你正在调试涉及多种语言的问题（例如，一个在 C 库中的错误通过 Python 绑定表现出来），LLMs 可以帮助导航不同层次。它们特别擅长理解 FFI 边界、构建系统问题和跨语言调试（例如，我的程序出错，但我认为是因为我的依赖项中的一个错误）。
- **Correlating symptoms with root causes**: “My program works fine but uses 10x more memory than expected” is the kind of vague symptom that LLMs can help investigate, suggesting likely causes and what to look for.关联症状与根本原因：“我的程序运行正常但比预期多使用 10 倍的内存”是 LLMs 可以协助调查的模糊症状，它提示了可能的原因和需要查找的内容。
- **Analyzing crash dumps and stack traces**: Paste a stack trace and ask what might have caused it.分析崩溃转储和堆栈跟踪：粘贴一个堆栈跟踪并询问可能导致它的原因。

›››note 5注意 5›››

> **Note on debug symbols**: For meaningful stack traces and debugging, ensure your binaries (and any linked libraries) are compiled with debug symbols (`-g` flag). Debug information is typically stored in DWARF format. Additionally, compiling with frame pointers (`-fno-omit-frame-pointer`) makes stack traces more reliable, especially for profiling tools. Without these, stack traces may show only memory addresses or be incomplete. This matters more for natively compiled programs (C++, Rust) than Python or Java.

**Limitations to keep in mind:需要注意的限制：**

- LLMs can hallucinate plausible-sounding but wrong explanationsLLMs 可能会编造听起来合理但错误的解释
- They may suggest fixes that mask the bug rather than fix it它们可能会提出掩盖错误而非修复错误的解决方案
- Always verify suggestions with actual debugging tools始终使用实际调试工具验证建议
- They work best as a complement to, not replacement for, understanding your code它们最适合作为理解代码的补充，而非替代

›››note 6注意 6›››

# Profiling分析

Even if your code functionally behaves as you would expect, that might not be good enough if it takes all your CPU or memory in the process. Algorithms classes often teach big *O* notation but not how to find hot spots in your programs. Since [premature optimization is the root of all evil](https://wiki.c2.com/?PrematureOptimization), you should learn about profilers and monitoring tools. They will help you understand which parts of your program are taking most of the time and/or resources so you can focus on optimizing those parts.即使你的代码在功能上表现符合预期，但如果它占用了你所有的 CPU 或内存，那可能还不够好。算法课程通常教授大 O 符号，但并不教如何找到程序中的热点。由于过早优化是万恶之源，你应该学习使用剖析器和监控工具。它们将帮助你了解程序中哪些部分占用了大部分时间或资源，从而让你能够专注于优化这些部分。

## Timing计时

The simplest way to measure performance is to time things. In many scenarios it can be enough to just print the time it took your code between two points.衡量性能最简单的方法是计时。在许多情况下，只需打印代码在两个点之间所花费的时间就足够了。

However, wall clock time can be misleading since your computer might be running other processes at the same time or waiting for events to happen. The `time` command distinguishes between *Real*, *User*, and *Sys* time:然而，墙上时钟时间可能会具有误导性，因为你的计算机可能同时运行其他进程或等待事件发生。 `time` 命令可以区分真实、用户和系统时间：

- **Real** - Wall clock time from start to finish, including time spent waiting真实墙钟时间，从开始到结束，包括等待时间
- **User** - Time spent in the CPU running user code用户 - CPU 运行用户代码所花费的时间
- **Sys** - Time spent in the CPU running kernel code系统 - CPU 运行内核代码所花费的时间

```bash
$ time curl https://missing.csail.mit.edu &> /dev/null
real	0m0.272s
user	0m0.079s
sys	    0m0.028s
```

Here the request took nearly 300 milliseconds (real time) but only 107ms of CPU time (user + sys). The rest was waiting for the network.在这里，请求花费了将近 300 毫秒（真实时间），但只有 107 毫秒的 CPU 时间（用户+系统）。其余时间是在等待网络。

## Resource Monitoring资源监控

Sometimes the first step towards analyzing the performance of your program is to understand what its actual resource consumption is. Programs often run slowly when they are resource constrained.分析程序性能的第一步有时是了解其实际资源消耗情况。当程序资源受限时，它们往往运行缓慢。

- **General Monitoring**: [htop](https://htop.dev/) is an improved version of `top` that presents various statistics for currently running processes. Useful keybinds: `<F6>` to sort processes, `t` to show tree hierarchy, `h` to toggle threads. There’s also [btop](https://github.com/aristocratos/btop) which monitors *way* more things.通用监控： `htop` 是 `top` 的改进版本，它显示当前运行进程的各种统计数据。有用的快捷键： `<F6>` 用于排序进程， `t` 用于显示树形结构， `h` 用于切换线程。还有 `btop` 可以监控更多内容。
- **I/O Operations**: [iotop](https://www.man7.org/linux/man-pages/man8/iotop.8.html) displays live I/O usage information.I/O 操作： `iotop` 显示实时 I/O 使用信息。
- **Memory Usage**: [free](https://www.man7.org/linux/man-pages/man1/free.1.html) displays total free and used memory.内存使用情况： `free` 显示总空闲和已用内存。
- **Open Files**: [lsof](https://www.man7.org/linux/man-pages/man8/lsof.8.html) lists file information about files opened by processes. Useful for checking which process has opened a specific file.打开的文件： `lsof` 列出进程打开的文件信息。可用于检查哪个进程打开了特定文件。
- **Network Connections**: [ss](https://www.man7.org/linux/man-pages/man8/ss.8.html) lets you monitor network connections. A common use case is figuring out what process is using a given port: `ss -tlnp | grep :8080`.网络连接： `ss` 可让你监控网络连接。常见用法是找出使用特定端口的进程： `ss -tlnp | grep :8080` 。
- **Network Usage**: [nethogs](https://github.com/raboof/nethogs) and [iftop](https://pdw.ex-parrot.com/iftop/) are good interactive CLI tools for monitoring network usage per process.网络使用情况： `nethogs` 和 `iftop` 是监控每个进程网络使用情况的优秀交互式 CLI 工具。

## Visualizing Performance Data可视化性能数据

Humans spot patterns in graphs much faster than in tables of numbers. When analyzing performance, plotting your data often reveals trends, spikes, and anomalies that would be invisible in raw numbers.人类在图形中识别模式的速度远快于在数字表格中。在分析性能时，将数据绘制成图表往往能揭示原始数字中无法显现的趋势、峰值和异常情况。

**Making data plottable**: When adding print or log statements for debugging, consider formatting the output so it can be easily graphed later. A simple timestamp and value in CSV format (`1705012345,42.5`) is much easier to plot than a prose sentence. JSON-structured logs can also be parsed and plotted with minimal effort. In other words, log your data [in a tidy way](https://vita.had.co.nz/papers/tidy-data.pdf).使数据可绘制：在添加用于调试的打印或日志语句时，考虑将输出格式化为稍后可以轻松绘制的格式。CSV 格式（ `1705012345,42.5` ）中的简单时间戳和值比一段散文句子更容易绘制。结构化的 JSON 日志也可以通过少量工作被解析并绘制。换句话说，以整洁的方式记录你的数据。

**Quick plotting with gnuplot**: For simple command-line plotting, [gnuplot](http://www.gnuplot.info/) can generate graphs directly from data files:使用 gnuplot 快速绘图：对于简单的命令行绘图， `gnuplot` 可以直接从数据文件生成图表：

```bash
# Plot a simple CSV with timestamp,value
gnuplot -e "set datafile separator ','; plot 'latency.csv' using 1:2 with lines"
```

**Iterative exploration with matplotlib and ggplot2**: For deeper analysis, Python’s [matplotlib](https://matplotlib.org/) and R’s [ggplot2](https://ggplot2.tidyverse.org/) enable iterative exploration. Unlike one-off plotting, these tools let you quickly slice and transform data to investigate hypotheses. ggplot2’s facet plots are particularly powerful—you can split a single dataset across multiple subplots by category (e.g., faceting request latency by endpoint or time-of-day) to tease out patterns that would otherwise be hidden.使用 matplotlib 和 ggplot2 进行迭代探索：为了进行更深入的分析，Python 的 `matplotlib` 和 R 的 `ggplot2` 能够实现迭代探索。与一次性绘图不同，这些工具允许你快速切片和转换数据以验证假设。ggplot2 的分组图特别强大——你可以通过类别将单个数据集分割到多个子图上（例如，按端点或一天中的时间分组绘制请求延迟），从而揭示原本隐藏的模式。

**Example use cases:示例用例：**

- Plotting request latency over time reveals periodic slowdowns (garbage collection, cron jobs, traffic patterns) that raw percentiles obscure绘制请求延迟随时间的变化可以揭示周期性减速（垃圾回收、定时任务、流量模式），而原始百分位数会掩盖这些问题
- Visualizing insert times for a growing data structure can expose algorithmic complexity issues—a plot of vector insertions will show characteristic spikes when the backing array doubles in size可视化增长数据结构的插入时间可以暴露算法复杂性问题——当支持数组大小翻倍时，向量插入的图表将显示出特征性尖峰
- Faceting metrics by different dimensions (request type, user cohort, server) often reveals that a “system-wide” problem is actually isolated to one category通过不同维度（请求类型、用户群体、服务器）对指标进行细分，通常会发现所谓的“全局问题”实际上仅限于某一特定类别

## CPU ProfilersCPU 分析器

Most of the time when people refer to *profilers* they mean *CPU profilers*. There are two main types:当人们提到分析器时，通常指的是 CPU 分析器。主要有两种类型：

- **Tracing profilers** keep a record of every function call your program makes跟踪分析器会记录你的程序所进行的每个函数调用
- **Sampling profilers** probe your program periodically (commonly every millisecond) and record the program’s stack采样分析器会定期（通常每毫秒）探测你的程序并记录程序的堆栈

Sampling profilers have lower overhead and are generally preferred for production use.采样分析器具有较低的额外开销，通常更受生产环境的使用青睐。

`perf stat` gives you a quick overview of where time is spent:`perf stat` 可以让你快速了解时间花费在哪里：

### Valgrind’s Callgrind: the tracing profilerValgrind 的 Callgrind：跟踪分析器

[callgrind](https://valgrind.org/docs/manual/cl-manual.html) is a profiling tool that records the call history and instruction counts of your program. function merge_sort(arr):
    if length(arr) <= 1:
        return arr
    mid = length(arr) / 2
    left = merge_sort(arr[0..mid])
    right = merge_sort(arr[mid..end])
    return merge(left, right)

function merge(left, right):
    result = []
    i = 0, j = 0
    while i < length(left) AND j < length(right):
        if left[i] <= right[j]:
            append result, left[i]
            i = i + 1
        else:
            append result, right[i]
            j = j + 1
    append remaining elements from left and right
    return result
``` Test vector: `merge_sort([3, 1, 4, 1, 5, 9, 2, 6])` should return `[1, 1, 2, 3, 4, 5, 6, 9]`. This matters more for natively compiled programs (C++, Rust) than Python or Java.[Back to note 5](https://missing-semester-cn.github.io/2026/debugging-profiling/#sidenote-ref-5)关于调试符号：为了获得有意义的堆栈跟踪和调试信息，请确保您的二进制文件（以及任何链接的库）使用调试符号编译（ `-g` 标志）。调试信息通常以 DWARF 格式存储。此外，使用帧指针（ `-fno-omit-frame-pointer` ）编译可以使堆栈跟踪更可靠，特别是对于分析工具。如果没有这些，堆栈跟踪可能只显示内存地址或是不完整的。这对于原生编译的程序（C++、Rust）比 Python 或 Java 更重要。 ↩
