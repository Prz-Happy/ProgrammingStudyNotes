# 打包与运输代码

## 概述
### 核心问题：让代码在自己机器上运行 vs 让别人也能运行
### 运输代码 = 将代码转换为他人无需精确复现你的环境即可使用的形式
### 取决于：编程语言 / 系统库 / 操作系统 / 构建类型（库/CLI/Web服务）
### 共同模式：定义工件(artifact) + 声明对环境的假设
### 本课八大主题：依赖/工件/版本/可重复性/容器/配置/编排/发布
### 示例以Python为主，概念跨语言通用

## 依赖项与环境

### 依赖问题
#### 程序委托逻辑给库 → 产生依赖关系
#### pip install requests 的4步流程
##### 1. 在PyPI中搜索requests
##### 2. 搜索匹配平台的合适工件
##### 3. 解决依赖关系（传递依赖的兼容版本）
##### 4. 下载 → 解压 → 复制到文件系统正确位置
#### 示例：requests依赖 certifi, charset-normalizer, idna, urllib3
#### 不同语言的依赖工具
##### Rust：cargo（统一工具链：构建+测试+依赖+发布）
##### Python：规范统一，工具多元（pip vs uv, setuptools vs hatch vs poetry）
##### LaTeX：TeX Live/MacTeX预装数千包

### 依赖冲突与"依赖地狱"
#### 场景：tensorflow要求numpy<1.19，pandas要求numpy>=1.16.5，另一包要求numpy>=1.19 → 无解
#### 解决方案：虚拟环境隔离
#### Python venv
##### python -m venv venv → 创建
##### source venv/bin/activate → 激活
##### 效果：独立的Python运行时+独立的包集
##### 好习惯：每个项目一个venv
#### 不要修改OS自带的Python（OS可能依赖它）

### 现代工具链：uv
#### pip install uv → 安装
#### uv pip install → 同接口，速度快数十倍（12ms解析 vs 传统分钟级）
#### uv venv --python 3.12 venv312 → 创建指定版本环境
#### 多Python版本管理：轻松切换3.12/3.11
#### 其他语言：项目自动获得独立环境+语言版本管理

## 组件与打包

### 源码 vs 工件
#### 源码：开发者编写和阅读
#### 工件：打包后、可分发的输出
#### 问题：切换到不同目录 import 失败（Python仅搜索特定位置）
#### 打包解决：将代码安装到已知位置

### Python 打包体系
#### 工件格式：轮子(.whl) — zip存档，含代码+元数据+安装说明
#### 项目清单：pyproject.toml（现代推荐，替代requirements.txt/setup.py）
#### 最小pyproject.toml结构
##### [project] — name/version/description/dependencies
##### [project.scripts] — CLI入口点（greet = "greeting:main"）
##### [build-system] — 构建后端（setuptools>=61.0）
#### uv build → 生成 .whl + .tar.gz
#### unzip -l 查看轮子内容（代码+META+WHEEL+RECORD）
#### uv pip install ./xxx.whl → 安装本地轮子
#### 局限性：平台特定依赖（CUDA）需要为不同平台/架构构建不同轮子

### 源码安装 vs 预构建二进制
#### 源码安装：下载代码 → 本地编译（需编译器+时间）
#### 预构建二进制：下载已编译工件（快+简单，但需匹配平台）
#### 示例：ripgrep发布页 → Linux(x86_64/ARM) + macOS(Intel/Apple Silicon) + Windows

## 发布与版本控制

### 发布概念
#### 开发环境 vs 生产环境：代码需在开发环境验证后才能发布到生产
#### 版本标识符：跟踪库随时间演变的离散快照
#### 变更日志：记录版本间变化的文档

### 语义版本控制（SemVer）
#### MAJOR.MINOR.PATCH（如 1.2.3）
##### PATCH 1.2.3→1.2.4：仅错误修复，完全向后兼容
##### MINOR 1.2.3→1.3.0：向后兼容的新功能
##### MAJOR 1.2.3→2.0.0：破坏性变更，需修改代码
#### 注意：0.x版本无SemVer保证（0.1.3→0.2.0可能有破坏性变更）
#### 版本规范符
##### == 精确版本
##### >= 最低版本
##### >=X,<Y 范围
##### ~= 兼容版本（Python特有，~=2.1.0 ≡ >=2.1.0,<2.2.0）
##### ^ 等价于npm/cargo的兼容符

### 日历版本控制（CalVer）
#### 基于日期而非语义：Ubuntu 24.04 / 24.10
#### 优点：一眼看出年代
#### 缺点：不传达兼容性信息
### SemVer并非万无一失：维护者偶尔在minor/patch引入破坏性变更

## 可重复性

### 固定依赖
#### 固定库 = 指定确切版本（==）而非范围（>=）
#### 锁定文件：保存满足所有约束的具体版本列表 → 可重复构建
#### uv lock → 生成uv.lock（含URL+哈希）

### 库 vs 应用/服务
#### 库：被其他代码导入 → 指定版本范围（最大化兼容性）
#### 应用/服务：最终消费者 → 锁定确切版本（确保可重复性）

### 封闭式构建
#### Nix / Bazel：编译器+系统库+构建环境全部固定，按内容寻址
#### NixOS：整个计算机配置版本控制 → 轻松复制环境

### 安全与更新的平衡
#### 新版本带来兼容问题 vs 旧版本暴露安全漏洞
#### CI管道：测试新版本兼容性 + Dependabot自动检测新版本
#### 出问题时：制定回滚计划 → 撤销升级，部署已知良好版本

## 虚拟机与容器

### 为什么需要容器
#### 包管理器不够：GPU驱动/特定编译器/系统库（OpenSSL）需全局安装
#### 传统方案：虚拟机 — 抽象整个计算机，独立OS
#### 现代方案：容器 — 共享主机内核，但隔离应用+依赖

### Docker
#### 镜像(Image) vs 容器(Container)
##### 镜像 = 打包的工件（模板）
##### 容器 = 镜像的运行实例
##### 一个镜像可运行多个容器
##### 镜像按层构建（Dockerfile每条指令一层）→ 缓存加速重建
#### Dockerfile基础
##### FROM python:3.12 → 基础镜像
##### RUN → 安装系统依赖
##### COPY → 复制文件进镜像
##### WORKDIR → 设置工作目录
#### Dockerfile最佳实践
##### 使用slim版镜像（python:3.12-slim）
##### 合并RUN命令减少层数 + 清理apt缓存
##### 版本锁定 + 不root运行
##### Builder模式：从另一镜像复制预构建二进制（如uv），不含编译工具
#### Docker局限性
##### 平台特定：linux/amd64 ↔ linux/arm64需模拟
##### macOS/Windows上实际运行轻量Linux VM（额外开销）
##### 隔离不如VM：共享内核（多租户安全隐患）
#### Nix flakes：按项目管理系统级库的替代方案

## 配置

### 核心原则：同一代码库通过仅改配置部署到不同环境
### 配置方式
#### 环境变量
##### os.environ.get("KEY", "default") → 可选+默认值
##### os.environ["KEY"] → 必需（缺失会报错）
#### 配置文件（YAML/JSON/TOML）
##### yaml.load → 结构化配置
##### database.url / server.port / debug 等
### 密钥管理
#### 敏感数据（API密钥等）绝不能进版本控制
#### 通过环境变量或密钥管理服务注入

## 服务与编排

### 微服务架构
#### 现代应用 = Web服务 + 数据库 + 缓存(Redis/Memcached) + 消息队列
#### 每个组件独立开发、部署、扩展
#### 通过网络（HTTP API）通信

### Docker Compose
#### 一个YAML定义所有服务 → 一起编排
#### docker-compose.yml示例
##### services: web + cache(Redis)
##### ports映射 / environment环境变量 / depends_on依赖顺序
##### volumes持久化数据
#### docker compose up → 一起启动
#### Docker内部DNS：服务名自动解析（web→cache:6379）

### Systemd管理容器
#### systemd unit文件 → 开机自启 + 失败重启
#### 标准控制：systemctl start/stop/status myapp
#### Requires=docker.service / After=docker.service

### Kubernetes (k8s)
#### 跨机器集群管理数千容器
#### 可扩展性+容错+高可用
#### 但学习曲线陡峭，小项目大材小用

## 发布

### 分发形式
#### 最简单：上传工件到HTTP目录供下载（如Ubuntu包存档）
#### GitHub Releases：预构建二进制附加到标记版本
#### pip install git+https://... → 从GitHub源码安装
#### pip install URL → 直接从GitHub Release安装轮子
#### Go去中心化模型：模块直接从源码仓库分发（无中央注册表）

### 包注册表（Package Registries）
#### Python → PyPI（pip/uv从那里下载）
#### Rust → crates.io
#### JavaScript → npm
#### Ruby → RubyGems
#### 容器 → Docker Hub
#### 私有/内部 → 自建PyPI服务器 / 私有Docker Registry / 云服务商管理方案

### 发布到PyPI
#### uv publish --publish-url https://test.pypi.org/legacy/ → 发布到TestPyPI
#### TestPyPI：测试发布流程，不污染真实PyPI
#### uv pip install --index-url https://test.pypi.org/simple/ → 从TestPyPI安装

### 轮子命名规范
#### py3-none-any → 纯Python，任意平台
#### cp312-macosx_14_0_arm64 → CPython 3.12, macOS 14+, Apple Silicon

### 信任与安全
#### 校验和验证完整性 / 包签名提供加密证明
### 部署网站需要：域名+DNS+反向代理(nginx)+HTTPS
### GitHub Pages：直接从仓库免费托管静态网站
