# 打包与运输代码 · 你 CS 教育的缺失学期 --- Packaging and Shipping Code · the missing semester of your cs education

# 打包和运输代码

让代码按预期工作很困难；让同样的代码在不同于你自己的机器上运行通常更困难。

运输代码意味着将你编写的代码转换成其他人可以在没有你电脑精确设置的情况下运行的可使用形式。运输代码有多种形式，取决于编程语言、系统库和操作系统等多种因素。它还取决于你在构建什么：一个软件库、一个命令行工具和一个网络服务都有不同的要求和部署步骤。无论如何，所有这些场景之间有一个共同的模式：我们需要定义交付物是什么——即所谓的 *工件*——以及它对周围环境做了哪些假设。

在本讲座中，我们将涵盖：

- [依赖项与环境](https://missing-semester-cn.github.io/2026/shipping-code/#dependencies--environments)
- [工件与打包](https://missing-semester-cn.github.io/2026/shipping-code/#artifacts--packaging)
- [发布与版本控制](https://missing-semester-cn.github.io/2026/shipping-code/#releases--versioning)
- [可重复性](https://missing-semester-cn.github.io/2026/shipping-code/#reproducibility)
- [虚拟机与容器](https://missing-semester-cn.github.io/2026/shipping-code/#vms--containers)
- [配置](https://missing-semester-cn.github.io/2026/shipping-code/#configuration)
- [服务与编排](https://missing-semester-cn.github.io/2026/shipping-code/#services--orchestration)
- [发布](https://missing-semester-cn.github.io/2026/shipping-code/#publishing)

我们将通过 Python 生态系统中的实例来解释这些概念，因为具体的例子有助于理解。虽然其他编程语言生态系统中的工具不同，但概念大体上是相同的。

# 依赖项和环境

在现代软件开发中，抽象层次无处不在。程序自然会将其逻辑委托给其他库或服务。然而，这会在你的程序与其运行所需的库之间引入一个 *依赖* 关系。例如，在 Python 中，为了获取网站的内容，我们通常这样做：

```python
import requests

response = requests.get("https://missing.csail.mit.edu")
```

然而，`requests` 库并没有随 Python 运行时捆绑在一起，所以如果我们尝试在未安装 `requests` 的情况下运行这段代码，Python 会抛出一个错误：

```console
$ python fetch.py
Traceback (most recent call last):
  File "fetch.py", line 1, in <module>
    import requests
ModuleNotFoundError: No module named 'requests'
```

为了使这个库可用，我们需要首先运行 `pip install requests` 来安装它。 `pip` 是 Python 编程语言提供的用于安装包的命令行工具。执行 `pip install requests` 会产生以下一系列操作：

1. 在 Python 包索引（[PyPI](https://pypi.org/)）中搜索 requests
2. 搜索适用于我们运行平台的合适工件
3. 解决依赖关系——`requests` 库本身依赖于其他包，因此安装器必须找到所有传递依赖关系的兼容版本并提前安装它们
4. 下载工件，然后解压并将文件复制到文件系统的正确位置

```console
$ pip install requests
Collecting requests
  Downloading requests-2.32.3-py3-none-any.whl (64 kB)
Collecting charset-normalizer<4,>=2
  Downloading charset_normalizer-3.4.0-cp311-cp311-manylinux_x86_64.whl (142 kB)
Collecting idna<4,>=2.5
  Downloading idna-3.10-py3-none-any.whl (70 kB)
Collecting urllib3<3,>=1.21.1
  Downloading urllib3-2.2.3-py3-none-any.whl (126 kB)
Collecting certifi>=2017.4.17
  Downloading certifi-2024.8.30-py3-none-any.whl (167 kB)
Installing collected packages: urllib3, idna, charset-normalizer, certifi, requests
Successfully installed certifi-2024.8.30 charset-normalizer-3.4.0 idna-3.10 requests-2.32.3 urllib3-2.2.3
```

这里我们可以看到 `requests` 有自己的依赖项，例如 `certifi` 或 `charset-normalizer`，并且它们必须在安装 `requests` 之前安装。安装完成后，Python 运行时在导入该库时可以找到它。

```console
$ python -c 'import requests; print(requests.__path__)'
['/usr/local/lib/python3.11/dist-packages/requests']

$ pip list | grep requests
requests        2.32.3
```

编程语言在安装和发布库方面有不同的工具、约定和做法。在一些语言如 Rust 中，工具链是统一的—— `cargo` 负责构建、测试、依赖管理以及发布。在另一些语言如 Python 中，统一发生在规范级别——而不是单一工具，而是有标准化的规范定义了打包的工作方式，允许每个任务有多个竞争的工具 ( `pip` vs [uv](https://docs.astral.sh/uv/), `setuptools` vs [hatch](https://hatch.pypa.io/) vs [poetry](https://python-poetry.org/))。在一些生态系统如 LaTeX 中，发行版如 TeX Live 或 MacTeX 会预装数千个包。

引入依赖也会引入依赖冲突。冲突发生在程序需要相同依赖的不兼容版本时。例如，如果 `tensorflow==2.3.0` 需要 `numpy>=1.16.0,<1.19.0`，而 `pandas==1.2.0` 需要 `numpy>=1.16.5`，那么任何满足 `numpy>=1.16.5,<1.19.0` 的版本都是有效的。但如果你的项目中另一个包需要 `numpy>=1.19`，那么就没有任何有效的版本能满足所有约束，从而产生冲突。

这种情况——多个软件包需要相互不兼容的共享依赖版本——通常被称为*依赖地狱*。处理冲突的一种方法是将每个程序的依赖项隔离到各自的 *环境*中。在 Python 中，我们通过运行以下命令创建虚拟环境：

```console
$ which python
/usr/bin/python
$ pwd
/home/missingsemester
$ python -m venv venv
$ source venv/bin/activate
$ which python
/home/missingsemester/venv/bin/python
$ which pip
/home/missingsemester/venv/bin/pip
$ python -c 'import requests; print(requests.__path__)'
['/home/missingsemester/venv/lib/python3.11/site-packages/requests']

$ pip list
Package Version
------- -------
pip     24.0
```

你可以将环境视为语言运行时的一个完整独立版本，包含其自身的安装包集。这个虚拟环境或 venv 将安装的依赖与全局 Python 安装隔离开来。为每个项目创建一个包含其所需依赖的虚拟环境是一个好习惯。

›››注意 1›››

> While many modern operating systems ship with installations of programming language runtimes like Python, it is unwise to modify these installations since the OS might rely on them for its own functionality. Prefer using separate environments instead.

在某些语言中，安装协议不是由工具定义的，而是作为规范定义的。在 Python 中， [PEP 517](https://peps.python.org/pep-0517/) 定义了构建系统接口，而 [PEP 621](https://peps.python.org/pep-0621/) 指定了项目元数据如何在 `pyproject.toml` 中存储。这使开发者能够改进 `pip`，并产生更优化的工具，如 `uv`。要安装 `uv`，只需执行 `pip install uv`。

使用 `uv` 代替 `pip` 遵循相同的接口，但速度显著更快：

```console
$ uv pip install requests
Resolved 5 packages in 12ms
Prepared 5 packages in 0.45ms
Installed 5 packages in 8ms
 + certifi==2024.8.30
 + charset-normalizer==3.4.0
 + idna==3.10
 + requests==2.32.3
 + urllib3==2.2.3
```

›››注意 2›››

> We strongly recommend using `uv pip` instead of `pip` whenever possible as it dramatically reduces the installation time.

除了依赖隔离，环境还允许你拥有不同版本的编程语言运行时。

```console
$ uv venv --python 3.12 venv312
Using CPython 3.12.7
Creating virtual environment at: venv312

$ source venv312/bin/activate && python --version
Python 3.12.7

$ uv venv --python 3.11 venv311
Using CPython 3.11.10
Creating virtual environment at: venv311

$ source venv311/bin/activate && python --version
Python 3.11.10
```

这在您需要在多个 Python 版本上测试代码，或者项目需要特定版本时很有帮助。

›››注意 3›››

> In some programming languages, each project automatically gets its own environment for its dependencies rather than you creating it manually, but the principle is the same. Most languages these days also have a mechanism for managing multiple versions of the language on a single system, and then specifying which version to use for individual projects.

# 组件与打包

在软件开发中，我们区分源代码和组件。开发者编写和阅读源代码，而组件是由源代码生成的打包、可分发的输出——准备好进行安装或部署。组件可以简单到是一个我们运行的代码文件，也可以复杂到是一个包含应用程序所有必要部分的整个虚拟机。考虑以下示例，我们在当前目录中有一个 Python 文件 `greet.py`：

```console
$ cat greet.py
def greet(name):
    return f"Hello, {name}!"

$ python -c "from greet import greet; print(greet('World'))"
Hello, World!

$ cd /tmp
$ python -c "from greet import greet; print(greet('World'))"
ModuleNotFoundError: No module named 'greet'
```

当我们切换到不同目录时，导入会失败，因为 Python 仅在特定位置（当前目录、已安装的包和 `PYTHONPATH` 中的路径）搜索模块。打包通过将代码安装到已知位置来解决这个问题。

在 Python 中，打包一个库涉及生成一个可让包安装器如 `pip` 或 `uv` 使用的工件来安装相关文件。Python 工件被称为 *轮子*，包含安装包所需的所有信息：代码文件、关于包的元数据（名称、版本、依赖项），以及文件在环境中的放置说明。构建工件需要我们编写一个项目文件（也常被称为清单），详细说明项目的具体内容、所需依赖项、包的版本和其他信息。在 Python 中，我们使用 `pyproject.toml` 来实现这一目的。

›››注意 4›››

> `pyproject.toml` is the modern and recommended way. While earlier packaging methods like `requirements.txt` or `setup.py` are still supported, you should prefer `pyproject.toml` whenever possible.

这是一个提供命令行工具的库的最小 `pyproject.toml`：

```toml
[project]
name = "greeting"
version = "0.1.0"
description = "A simple greeting library"
dependencies = ["typer>=0.9"]

[project.scripts]
greet = "greeting:main"

[build-system]
requires = ["setuptools>=61.0"]
build-backend = "setuptools.build_meta"
```

`typer` 库是一个流行的 Python 包，用于创建命令行界面，具有极少的样板代码。

相应的 `greeting.py`：

```python
import typer

def greet(name: str) -> str:
    return f"Hello, {name}!"

def main(name: str):
    print(greet(name))

if __name__ == "__main__":
    typer.run(main)
```

有了这个文件，我们现在可以造轮子了：

```console
$ uv build
Building source distribution...
Building wheel from source distribution...
Successfully built dist/greeting-0.1.0.tar.gz
Successfully built dist/greeting-0.1.0-py3-none-any.whl

$ ls dist/
greeting-0.1.0-py3-none-any.whl
greeting-0.1.0.tar.gz
```

`.whl` 文件是轮包（一种具有特定结构的 zip 存档），而 `.tar.gz` 是为需要从源代码构建的系统提供的源代码分发。

您可以检查轮包的内容，以查看打包了什么内容：

```console
$ unzip -l dist/greeting-0.1.0-py3-none-any.whl
Archive:  dist/greeting-0.1.0-py3-none-any.whl
  Length      Date    Time    Name
---------  ---------- -----   ----
      150  2024-01-15 10:30   greeting.py
      312  2024-01-15 10:30   greeting-0.1.0.dist-info/METADATA
       92  2024-01-15 10:30   greeting-0.1.0.dist-info/WHEEL
        9  2024-01-15 10:30   greeting-0.1.0.dist-info/top_level.txt
      435  2024-01-15 10:30   greeting-0.1.0.dist-info/RECORD
---------                     -------
      998                     5 files
```

现在如果我们把这个轮子交给其他人，他们可以通过运行以下命令来安装它：

```console
$ uv pip install ./greeting-0.1.0-py3-none-any.whl
$ greet Alice
Hello, Alice!
```

这将把之前我们构建的库安装到他们的环境中，包括 `greet` 命令行工具。

这种方法存在一些局限性。特别是如果我们的库依赖于平台特定的库，例如用于 GPU 加速的 CUDA，那么我们的工件只能在安装了这些特定库的系统上工作，并且我们可能需要为不同的平台（Linux、macOS、Windows）和架构（x86、ARM）构建不同的轮子。

在安装软件时，从源代码安装和安装预构建的二进制文件之间存在重要区别。从源代码安装意味着下载原始代码并在您的机器上编译它——这需要安装编译器和构建工具，并且对于大型项目可能需要大量时间。

安装预构建的二进制文件意味着下载由他人已编译好的工件——更快更简单，但二进制文件必须与您的平台和架构匹配。例如， [ripgrep 的发布页面](https://github.com/BurntSushi/ripgrep/releases)显示了适用于 Linux（x86_64、ARM）、macOS（Intel、Apple Silicon）和 Windows 的预构建二进制文件。

# 发布与版本控制

代码在持续构建过程中，但发布是离散的。在软件开发中，开发环境和生产环境之间有明确的区别。代码需要在开发环境中经过验证后才能被 *发布*到生产环境。发布过程包括多个步骤，包括测试、依赖管理、版本控制、配置、部署和发布。

软件库不是静态的，会随着时间的推移进行修复和添加新功能。我们通过离散的版本标识符来跟踪这种演变，这些标识符对应于库在某个时间点的状态。库行为的变化范围可以从修复非关键功能的补丁，到扩展其功能的全新特性，再到破坏向后兼容性的变更。变更日志记录了版本引入的变化——这些是软件开发人员用来沟通新版本相关变更的文档。

然而，要跟踪每个依赖项的持续变化是不切实际的，考虑到传递依赖项——即我们依赖项的依赖项——这种情况更加如此。

›››注意 5›››

> You can visualize the entire dependency tree of your project with `uv tree`, which shows all packages and their transitive dependencies in a tree format.

为了简化这个问题，软件版本化有一些约定俗成的做法，其中最普遍的是[语义版本化](https://semver.org/)或 SemVer。在语义版本化中，版本的形式为 MAJOR.MINOR.PATCH，每个值都是整数。简而言之，升级：

- PATCH（例如，1.2.3 → 1.2.4）应仅包含错误修复，并完全向后兼容
- MINOR（例如，1.2.3 → 1.3.0）以向后兼容的方式添加新功能
- MAJOR（例如，1.2.3 → 2.0.0）表示可能需要代码修改的破坏性变更

›››注意 6›››

> This is a simplification and we encourage reading the full SemVer specification to understand for instance why going from 0.1.3 to 0.2.0 might cause breaking changes or what 1.0.0-rc.1 means. Python packaging supports semantic versioning natively, so when we specify the versions of our dependencies we can use various specifiers:

在 `pyproject.toml` 中，我们有多种方式来约束我们依赖项的兼容版本范围：

```toml
[project]
dependencies = [
    "requests==2.32.3",  # Exact version - only this specific version
    "click>=8.0",        # Minimum version - 8.0 or newer
    "numpy>=1.24,<2.0",  # Range - at least 1.24 but less than 2.0
    "pandas~=2.1.0",     # Compatible release - >=2.1.0 and <2.2.0
]
```

版本规范符存在于许多包管理器（npm、cargo 等）中，且具有不同的精确语义。``~=`` 运算符是 Python 的“兼容版本”运算符——``~=2.1.0`` 表示“任何与 2.1.0 兼容的版本”，这等价于 ``>=2.1.0`` 和 ``<2.2.0``。这大致等同于 npm 和 cargo 中的尖号（``^``）运算符，后者遵循 SemVer 的兼容性概念。

并非所有软件都使用语义版本控制。一种常见的替代方案是日历版本控制（CalVer），在这种方式中，版本是基于发布日期而非语义意义。例如，Ubuntu 使用类似 `24.04`（2024 年 4 月）和 `24.10`（2024 年 10 月）的版本。CalVer 可以轻松看出一个发布的年代，但它并不传达任何关于兼容性的信息。最后，语义版本控制并非万无一失，有时维护者在次要版本或补丁版本中会无意中引入破坏性变更。

# 可重复性

在现代软件开发中，你编写的代码位于许多抽象层之上。这包括你的编程语言运行时、第三方库、操作系统，甚至硬件本身。这些层中的任何差异都可能改变代码的行为，甚至阻止其按预期运行。此外，底层硬件的差异也会影响你发布软件的能力。

固定库指的是指定确切版本而不是版本范围，例如 `requests==2.32.3` 而不是 `requests>=2.0`。

包管理器的一部分工作是为依赖项（包括传递依赖项）提供的所有约束进行考虑，然后生成一个满足所有约束的有效版本列表。然后可以将这些具体的版本列表保存到文件中以实现可重复性；这些文件被称为 *锁定文件*。

```console
$ uv lock
Resolved 12 packages in 45ms

$ cat uv.lock | head -20
version = 1
requires-python = ">=3.11"

[[package]]
name = "certifi"
version = "2024.8.30"
source = { registry = "https://pypi.org/simple" }
sdist = { url = "https://files.pythonhosted.org/...", hash = "sha256:..." }
wheels = [
    { url = "https://files.pythonhosted.org/...", hash = "sha256:..." },
]
...
```

在处理依赖版本控制和可重复性时，一个关键的区分是库与应用/服务之间的不同。库的设计目的是被其他可能有自己的依赖的代码导入和使用，因此指定过于严格的版本约束可能会与用户的其他依赖产生冲突。相比之下，应用或服务是软件的最终消费者，通常通过用户界面或 API 而不是编程接口来暴露其功能。对于库，指定版本范围是良好的实践，以最大限度地提高与更广泛的软件包生态系统的兼容性。对于应用，锁定确切版本可以确保可重复性——运行该应用的所有人都使用完全相同的依赖。

对于需要最大程度可重复性的项目，像 [Nix](https://nixos.org/) 和 [Bazel](https://bazel.build/) 这样的工具提供 *封闭式* 构建——其中所有输入，包括编译器、系统库，甚至构建环境本身都被固定并按内容寻址。这保证了无论何时何地运行构建，输出都是逐位完全相同的。

›››注意 7›››

> You can even use NixOS to manage your entire computer install so that you can trivially spin up new copies of your computer setup and manage their complete configuration through version-controlled configuration files.

软件开发中一个永无止境的紧张关系是，新软件版本有意或无意地引入了不兼容问题，而另一方面，旧软件版本随着时间的推移会逐渐暴露出安全漏洞。我们可以通过使用持续集成管道（我们将在《 [代码质量与 CI](https://missing-semester-cn.github.io/2026/code-quality/)》讲座中了解更多）来解决这个问题，这些管道会测试我们的应用程序与新软件版本的兼容性，并设置自动化机制来检测我们依赖项的新版本发布，例如《[Dependabot](https://github.com/dependabot)》。

即使有 CI 测试机制，在升级软件版本时仍然会出现问题，这通常是因为开发环境和生产环境之间不可避免的差异。在这种情况下，最好的做法是制定一个《 *回滚*》计划，即撤销版本升级，重新部署一个已知良好的版本。

# 虚拟机与容器

随着你开始依赖更复杂的依赖项，你代码的依赖项很可能超出包管理器能够处理的范围。一个常见的原因是需要与特定的系统库或硬件驱动程序进行交互。例如，在科学计算和人工智能领域，程序通常需要专门的库和驱动程序来利用 GPU 硬件。许多系统级依赖项（如 GPU 驱动程序、特定版本的编译器、OpenSSL 等共享库）仍然需要全局安装。

传统上，这个更广泛的依赖问题是通过虚拟机（VMs）解决的。虚拟机抽象了整个计算机，并提供了一个完全隔离的环境，拥有自己的专用操作系统。一种更现代的方法是容器，它将应用程序及其依赖项、库和文件系统打包在一起，但共享主机的操作系统内核，而不是虚拟化整个计算机。由于它们共享内核，容器比虚拟机更轻量级，启动更快，运行更高效。

最受欢迎的容器平台是 [Docker](https://www.docker.com/)。Docker 引入了一种标准化的方法来构建、分发和运行容器。在底层，Docker 使用 containerd 作为其容器运行时——这是一个行业标准，其他工具如 Kubernetes 也使用它。

运行容器很简单。例如，要在容器内运行 Python 解释器，我们使用 `docker run`（`-it` 标志使容器可以通过终端进行交互。当你退出时，容器会停止。）

```console
$ docker run -it python:3.12 python
Python 3.12.7 (main, Nov  5 2024, 02:53:25) [GCC 12.2.0] on linux
>>> print("Hello from inside a container!")
Hello from inside a container!
```

在实际应用中，你的程序可能依赖于整个文件系统。为了解决这个问题，我们可以使用容器镜像，将应用程序的整个文件系统作为工件进行打包。容器镜像是通过编程方式创建的。使用 Docker 时，我们通过 Dockerfile 语法指定镜像的精确依赖项、系统库和配置：

```dockerfile
FROM python:3.12
RUN apt-get update
RUN apt-get install -y gcc
RUN apt-get install -y libpq-dev
RUN pip install numpy
RUN pip install pandas
COPY . /app
WORKDIR /app
RUN pip install .
```

一个重要的区别：Docker **镜像** 是打包的工件（如模板），而 **容器** 是该镜像的运行实例。你可以从同一个镜像运行多个容器。镜像按层构建，Dockerfile 中的每条指令（`FROM`、`RUN`、`COPY` 等）都会创建一个新层。Docker 缓存这些层，所以如果你修改 Dockerfile 中的某一行，只需要重建该层及其后续层。

之前的 Dockerfile 存在几个问题：它使用了完整的 Python 镜像而不是精简版本，运行独立的 `RUN` 命令创建不必要的层，版本未锁定，并且没有清理包管理器缓存，导致传输了不必要的文件。其他常见错误包括以 root 身份不安全地运行容器，以及意外将密钥嵌入层中。

这是改进后的版本

```dockerfile
FROM python:3.12-slim
COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv
RUN apt-get update && \
    apt-get install -y --no-install-recommends gcc libpq-dev && \
    rm -rf /var/lib/apt/lists/*
COPY pyproject.toml uv.lock ./
RUN uv pip install --system -r uv.lock
COPY . /app
```

在之前的例子中我们看到，我们没有从源代码安装 `uv`，而是从 `ghcr.io/astral-sh/uv:latest` 镜像中复制预构建的二进制文件。这被称为 *builder* 模式。使用这种模式，我们不需要打包编译代码所需的所有工具，只需打包运行应用程序所需的最终二进制文件（在这个例子中是 `uv`）。

Docker 存在一些重要的局限性需要注意。首先，容器镜像通常是平台特定的——为 `linux/amd64` 构建的镜像在没有模拟的情况下无法在 `linux/arm64`（Apple Silicon Mac）上原生运行，模拟会非常慢。其次，Docker 容器需要 Linux 内核，因此在 macOS 和 Windows 上，Docker 实际上在底层运行一个轻量级的 Linux 虚拟机，增加了额外开销。第三，Docker 的隔离性不如虚拟机——容器共享主机内核，这在多租户环境中是一个安全隐患。

›››note 8›››

> These days, more projects are also making use of nix to manage even “system-wide” libraries and applications per project through [nix flakes](https://serokell.io/blog/practical-nix-flakes).

# 配置

软件天生就是可配置的。在[命令行环境](https://missing-semester-cn.github.io/2026/command-line-environment/)讲座中，我们看到程序通过标志、环境变量甚至配置文件（即点文件）接收选项。这对更复杂的应用程序同样适用，并且有成熟的模式来大规模管理配置。软件配置不应嵌入代码中，而应在运行时提供。常见的配置方式包括环境变量和配置文件。

这里有一个通过环境变量配置的应用程序的例子：

```python
import os

DATABASE_URL = os.environ.get("DATABASE_URL", "sqlite:///local.db")
DEBUG = os.environ.get("DEBUG", "false").lower() == "true"
API_KEY = os.environ["API_KEY"]  # Required - will raise if not set
```

一个应用程序也可以通过配置文件进行配置（例如，一个加载配置的 Python 程序通过 `yaml.load`），`config.yaml`:

```yaml
database:
  url: "postgresql://localhost/myapp"
  pool_size: 5
server:
  host: "0.0.0.0"
  port: 8080
  debug: false
```

一个关于配置的良好右手定则是：相同的代码库应该能够通过仅修改配置即可部署到不同的环境（开发、测试、生产），而无需修改代码。

在众多配置选项中，通常包含敏感数据，如 API 密钥。密钥需要谨慎处理以避免意外泄露，并且绝不能包含在版本控制中。

# 服务与编排

现代应用程序很少独立存在。一个典型的 Web 应用程序可能需要一个数据库用于持久化存储，一个缓存用于提升性能，一个消息队列用于后台任务，以及各种其他支持服务。现代架构通常将功能分解为可独立开发、部署和扩展的多个服务，而不是将所有内容捆绑成一个庞大的单体应用程序。

例如，如果我们确定我们的应用程序可能受益于使用缓存，我们就不需要自己开发，而是可以利用现有的经过实战检验的解决方案，比如 [Redis](https://redis.io/) 或 [Memcached](https://memcached.org/)。我们可以通过将 Redis 构建为容器的一部分来将其嵌入到我们的应用程序依赖中，但这意味着需要协调 Redis 和我们的应用程序之间的所有依赖关系，这可能具有挑战性，甚至可能不可行。相反，我们可以将每个应用程序分别部署在自己的容器中。这通常被称为微服务架构，其中每个组件都作为独立的服务运行，通过网络（通常通过 HTTP API）进行通信。

[Docker Compose](https://docs.docker.com/compose/) 是一个用于定义和运行多容器应用程序的工具。与其单独管理容器，你可以在一个 YAML 文件中声明所有服务，并将它们一起编排。现在我们的完整应用程序包含超过一个容器：

```yaml
# docker-compose.yml
services:
  web:
    build: .
    ports:
      - "8080:8080"
    environment:
      - REDIS_URL=redis://cache:6379
    depends_on:
      - cache

  cache:
    image: redis:7-alpine
    volumes:
      - redis_data:/data

volumes:
  redis_data:
```

使用 `docker compose up`，两个服务将一起启动，并且 Web 应用程序可以通过主机名 `cache` 连接到 Redis（Docker 的内部 DNS 会自动解析服务名称）。Docker Compose 让我们声明我们希望如何部署一个或多个服务，并处理它们一起启动的编排、设置它们之间的网络以及管理用于数据持久化的共享卷。

在生产环境中，通常希望 docker compose 服务在启动时自动启动，并在失败时重启。一种常见的方法是使用 systemd 来管理 docker compose 部署：

```ini
# /etc/systemd/system/myapp.service
[Unit]
Description=My Application
Requires=docker.service
After=docker.service

[Service]
Type=oneshot
RemainAfterExit=yes
WorkingDirectory=/opt/myapp
ExecStart=/usr/bin/docker compose up -d
ExecStop=/usr/bin/docker compose down

[Install]
WantedBy=multi-user.target
```

这个 systemd 单位文件确保在系统启动时（Docker 准备就绪后）启动您的应用程序，并提供标准控制，如 `systemctl start myapp`、`systemctl stop myapp` 和 `systemctl status myapp`。

随着部署需求日益复杂——需要跨多台机器实现可扩展性、在服务崩溃时具备容错能力，并确保高可用性——组织开始转向像 Kubernetes（k8s）这样复杂的容器编排平台，这些平台能够管理跨机器集群的数千个容器。但话说回来，Kubernetes 的学习曲线陡峭，运营开销巨大，因此对于较小的项目来说往往是大材小用。

这种多容器设置之所以部分可行，是因为现代服务通过标准化的 API（如 HTTP REST API）相互通信。例如，每当一个程序与 OpenAI 或 Anthropic 等 LLM 提供商交互时，其底层实际上会向其服务器发送 HTTP 请求并解析响应：

```console
$ curl https://api.anthropic.com/v1/messages \
    -H "x-api-key: $ANTHROPIC_API_KEY" \
    -H "content-type: application/json" \
    -H "anthropic-version: 2023-06-01" \
    -d '{"model": "claude-sonnet-4-20250514", "max_tokens": 256,
         "messages": [{"role": "user", "content": "Explain containers vs VMs in one sentence."}]}'
```

# 发布

一旦你的代码能正常工作，你可能想将其分发供其他人下载和安装。分发有多种形式，并且与你所使用的编程语言和环境密切相关。

最简单的分发形式是上传工件供人们下载并本地安装。这种方式仍然很常见，你可以在像 [Ubuntu 的软件包存档](http://archive.ubuntu.com/ubuntu/pool/main/) 这样的地方找到它，它本质上是一个列出 `.deb` 文件的 HTTP 目录。

如今，GitHub 已成为发布源代码和工件的默认平台。虽然源代码通常是公开可用的，但 GitHub Releases 允许维护者将预构建的二进制文件和其他工件附加到标记版本上。

包管理器有时支持直接从 GitHub 安装，无论是从源代码还是从预构建的轮包：

```console
# Install from source (will clone and build)
$ pip install git+https://github.com/psf/requests.git

# Install from a specific tag/branch
$ pip install git+https://github.com/psf/requests.git@v2.32.3

# Install a wheel directly from a GitHub release
$ pip install https://github.com/user/repo/releases/download/v1.0/package-1.0-py3-none-any.whl
```

事实上，一些语言如 Go 使用去中心化的分发模型——而不是中央包仓库，Go 模块直接从它们的源代码仓库分发。模块路径如 `github.com/gorilla/mux` 指示代码存放的位置，而 `go get` 直接从那里获取。然而，大多数包管理器如 `pip`、`cargo` 或 `brew` 都有预打包项目的中央索引，以便于分发和安装。如果我们运行

```console
$ uv pip install requests --verbose --no-cache 2>&1 | grep -F '.whl'
DEBUG Selecting: requests==2.32.5 [compatible] (requests-2.32.5-py3-none-any.whl)
DEBUG No cache entry for: https://files.pythonhosted.org/packages/1e/db/4254e3eabe8020b458f1a747140d32277ec7a271daf1d235b70dc0b4e6e3/requests-2.32.5-py3-none-any.whl.metadata
DEBUG No cache entry for: https://files.pythonhosted.org/packages/1e/db/4254e3eabe8020b458f1a747140d32277ec7a271daf1d235b70dc0b4e6e3/requests-2.32.5-py3-none-any.whl
```

我们会看到我们从哪里获取 `requests` 轮。注意文件名中的 `py3-none-any`——这意味着该轮适用于任何 Python 3 版本，在任何操作系统和任何架构上。对于包含编译代码的包，轮是平台特定的：

```console
$ uv pip install numpy --verbose --no-cache 2>&1 | grep -F '.whl'
DEBUG Selecting: numpy==2.2.1 [compatible] (numpy-2.2.1-cp312-cp312-macosx_14_0_arm64.whl)
```

这里 `cp312-cp312-macosx_14_0_arm64` 表示这个轮子是专门为在 macOS 14+ 的 ARM64（苹果硅）平台上的 CPython 3.12 设计的。如果你使用的是其他平台，`pip` 会下载不同的轮子或从源代码构建。

相反，为了让人们能够找到我们创建的包裹，我们需要将其发布到这些注册表之一。在 Python 中，主要的注册表是 [Python 包索引（PyPI）](https://pypi.org/)。与安装类似，发布包也有多种方法。 `uv publish` 命令提供了一个现代的界面，用于将包上传到 PyPI：

```console
$ uv publish --publish-url https://test.pypi.org/legacy/
Publishing greeting-0.1.0.tar.gz
Publishing greeting-0.1.0-py3-none-any.whl
```

这里我们使用 [TestPyPI](https://test.pypi.org/) — 一个独立的包注册中心，用于在不污染真实 PyPI 的情况下测试你的发布流程。一旦上传，你可以从 TestPyPI 安装：

```console
$ uv pip install --index-url https://test.pypi.org/simple/ greeting
```

发布软件时一个关键的考虑因素是信任。用户如何验证他们下载的软件包确实来自你且未被篡改？软件包注册表使用校验和来验证完整性，而一些生态系统支持软件包签名以提供作者身份的加密证明。

不同的语言有自己的软件包注册表：[crates.io](https://crates.io/) 用于 Rust，[npm](https://www.npmjs.com/) 用于 JavaScript，[RubyGems](https://rubygems.org/) 用于 Ruby，以及 [Docker Hub](https://hub.docker.com/) 用于容器镜像。同时，对于私有或内部软件包，组织通常会部署自己的软件包仓库（例如私有 PyPI 服务器或私有 Docker 注册表）或使用云服务提供商的管理解决方案。

将网络服务部署到互联网需要额外的基础设施：域名注册、DNS 配置以将你的域名指向服务器，并且通常需要一个反向代理如 nginx 来处理 HTTPS 和路由流量。对于简单的用例如文档或静态网站，[GitHub Pages](https://pages.github.com/) 提供直接从仓库免费托管的解决方案。

1. 用 `printenv` 将环境保存到文件中，创建一个 venv，激活它，再用 `printenv` 将环境保存到另一个文件中，然后运行 `diff before.txt after.txt`。环境发生了什么变化？为什么 shell 更偏好 venv？（提示：查看激活前后 `$PATH` 的变化。）运行 `which deactivate`，并思考 deactivate bash 函数的作用。

3. 安装 Docker 并使用它通过 docker compose 在本地构建 Missing Semester 课程网站。
4. 为一个简单的 Python 应用编写 Dockerfile。然后编写一个 `docker-compose.yml`，使其与 Redis 缓存一起运行。
5. 将 Python 包发布到 TestPyPI（除非值得分享，否则不要发布到真实的 PyPI！）。然后使用该包构建 Docker 镜像，并将其推送到 `ghcr.io`。
6. 使用 [GitHub Pages](https://docs.github.com/en/pages/quickstart) 制作一个网站。额外（非）积分：配置一个自定义域名。
