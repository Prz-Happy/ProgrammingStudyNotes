# 不止于代码
## 概述
### 优秀工程师 = 可维护代码 + 清晰沟通 + 认真贡献 + 生态好公民
## 单向沟通
### 核心：记录「为什么」而非「做了什么」（做了什么一目了然）
### 沟通对象：后来的队友 / 接手维护者 / 半年后的你
### 代码注释
#### 好注释解释代码本身无法表达的“为何”
#### 值得写的注释类型
##### TODO：标注未完成，留上下文（缺什么 / 为何延期）；“TODO: optimize”无价值
##### 参考资料：算法 / 借鉴代码 / 文档行为 → 永久链接 + 注明差异
##### 正确性说明：解释不寻常代码为何正确
##### 血泪教训：30分钟+调通且修复不明显 → 记下来
##### 常数的理由：魔法数字为何是这个值
##### 承重细节：正确性依赖的实现细节（如 BTreeSet 迭代顺序）
##### “为什么不用”：避开显而易见做法时说明，防止被“修复”
### README
#### 依次回答四问：做什么 / 为何在乎 / 如何使用 / 如何安装
#### 漏斗式组织：顶部一句话 + 视觉示意 → 逐步细节
#### 先展示用法再讲安装
### 提交信息
#### 代码库演进的历史记录（git blame 时解答“为什么”）
#### 提交正文回答：什么问题 / 备选方案 / 取舍影响 / 意外点
#### 复杂改动用「问题 → 解决方案 → 影响」结构
#### LLM 写提交：同会话写最好（自带上下文）；要求聚焦“为什么”并让它提问缺失上下文
#### 逻辑拆分提交：git add -p；一个提交一个连贯改动；利于评审和 git bisect
## 协作
### 贡献
#### 信噪比：用户>贡献者>维护者，维护者时间稀缺
#### 好的 bug 报告：环境 / 期望vs实际 / 复现步骤 / 已尝试
#### 安全漏洞：私下联系维护者（SECURITY.md），不公开发布
#### 搜索已有 issue：补充而非重复
#### 最小可复现示例 = 黄金
#### 跟进礼仪：一两周一次礼貌跟进；不每天催、不“我也是”、不贴大段输出
#### CONTRIBUTING.md 必须遵守；从小处开始（错别字/文档）
#### 许可证：贡献受同样约束；copyleft（GPL）注意派生作品开源
#### PR：隔离改动；说明“为什么”；大 PR 靠 commit hygiene
#### 优先上游贡献而非 fork
#### AI 生成代码：不理解就不能提交；保留打磨责任
#### 接受 PR = 承接长期责任 → 贡献者要论证价值
#### 收到反馈：代码不是你本人；不同意就提澄清问题
### 评审
#### 新人视角有价值：新鲜眼睛抓资深忽略的问题
#### 最快学习方式之一：模式 / 惯用法 / 可读性直觉
#### 额外收益：入库前抓 bug、传播知识、协作提升质量
#### 有效评审技巧
##### 评审代码而非评审人
##### 给可操作的建议而非空泛批评
##### 提问而非命令
##### 解释“为什么”
##### 区分阻断性问题 vs 建议
##### 肯定做得好的地方
##### 知道何时收手（聚焦大问题）
#### AI 不能替代人工评审：缺上下文、不理解产品需求
## 教学互助
### 提问是向任何人学习的技能（Julia Evans 两篇博客）
### 先陈述你的理解：“我认为是 X，对吗？”
### 多用是/否问题：避免跑题
### 具体一点：“LEFT JOIN 会包含右表没有匹配的行吗？”优于“SQL join 怎么回事？”
### 承认自己不理解：打断询问；“我不知道” + “不过我猜 / 可以去查”
### 不要接受不完整的答案：持续追问直到真正理解
### 先做些调研：基础调查让问题更有针对性
### 好问题让社区受益：揭示隐藏假设
### 同样适用于和 LLM 沟通
## AI 礼仪
### 有实质贡献要披露：诚实 / 设预期 / 恰当评审
### 说明用了 AI 的部分：“vibe coding 出来的” vs “写了备份工具，LLM 设计前端样式”
### 遵循团队 / 项目规范：严格政策（合规 / 数据驻留）
### 学习阶段：AI 全做会适得其反（学到的是写提示 / 审查输出）
### 面试评估：允许与否要问清；明确禁用就不许偷偷用
## 练习
### 1. 浏览知名项目源码找各类注释；思考缺失的代价
### 2. 对比提交历史中好坏提交信息；用「问题→方案→影响」改写
### 3. 对比三个 1000+ star 项目的 README，识别噪音
### 4. 评估未解决 issue 是否尊重维护者时间
### 5. 为 bug 创建最小可复现示例（记录剥离了什么）
### 6. 通读一个已合并 PR 的评审，评估评论效率
### 7. 对比 Stack Overflow 高票 vs 被踩问题，验证讲义建议
