# 版本控制与 Git · 你 CS 教育的缺失学期 --- Version Control and Git · the missing semester of your cs education

# Version Control and Git版本控制与 Git

Version control systems (VCSs) are tools used to track changes to source code (or other collections of files and folders). As the name implies, these tools help maintain a history of changes; furthermore, they facilitate collaboration. Logically, VCSs track changes to a folder and its contents in a series of *snapshots*, where each snapshot encapsulates the entire state of files/folders within a top-level directory. VCSs also maintain metadata like who created each snapshot, messages associated with each snapshot, and so on.版本控制系统（VCS）是用于跟踪源代码（或其他文件和文件夹集合）更改的工具。顾名思义，这些工具有助于维护更改历史；此外，它们还促进了协作。逻辑上，VCS 按一系列快照跟踪文件夹及其内容的更改，其中每个快照封装了顶层目录中文件/文件夹的完整状态。VCS 还维护元数据，例如谁创建了每个快照、与每个快照关联的消息等。

Why is version control useful? Even when you’re working by yourself, it can let you look at old snapshots of a project, keep a log of why certain changes were made, work on parallel branches of development, and much more. When working with others, it’s an invaluable tool for seeing what other people have changed, as well as resolving conflicts in concurrent development.为什么版本控制有用？即使你独自工作，它也能让你查看项目的旧快照、记录某些更改的原因、并行开发分支等。与他人合作时，它是一个宝贵的工具，可以查看其他人所做的更改，以及在并发开发中解决冲突。

现代版本控制系统还允许你轻松（并且经常自动）回答以下问题：

- 谁写了这个模块？
- 这个特定文件的这一行是什么时候被编辑的？由谁编辑？为什么编辑？
- 在过去的一千次修订中，某个特定的单元测试是什么时候/为什么停止工作的？

虽然存在其他版本控制系统，但 Git 已成为事实上的标准。这幅 XKCD 漫画捕捉了 Git 的声誉：

由于 Git 的界面是一种有漏洞的抽象，自上而下学习 Git（从其界面/命令行界面开始）会导致很多困惑。可以记住少数几个命令，并将它们视为魔法咒语，每当出现问题时就按照上面的漫画方法行事。

虽然 Git 的界面确实丑陋，但其底层设计和理念非常优美。丑陋的界面需要死记硬背，而优美的设计则可以理解。因此，我们从其数据模型开始，自下而上地解释 Git，随后会涵盖命令行界面。一旦理解了数据模型，就可以更好地理解命令是如何操作底层数据模型的。

# Git’s data modelGit 的数据模型

Git 的巧妙之处在于其精心设计的数据模型，该模型支持所有版本控制的优秀特性，如维护历史记录、支持分支以及促进协作。

## 快照

Git 将某个顶层目录内的一组文件和文件夹的历史记录建模为一系列快照。在 Git 术语中，文件被称为“blob”，它只是一堆字节。目录被称为“树”，它将名称映射到 blob 或树（因此目录可以包含其他目录）。快照是被跟踪的顶层树。例如，我们可能有一个如下所示的树：

```plaintext
<root> (tree)
|
+- foo (tree)
|  |
|  + bar.txt (blob, contents = "hello world")
|
+- baz.txt (blob, contents = "git is wonderful")
```

顶层树包含两个元素，一个树“foo”（它本身包含一个元素，一个 blob“bar.txt”），以及一个 blob“baz.txt”。

## 建模历史：关联快照

版本控制系统应该如何关联快照？一种简单的模型是采用线性历史。历史将是一系列按时间顺序排列的快照。出于多种原因，Git 不使用这种简单的模型。

在 Git 中，历史是一个有向无环图（DAG）的快照。这听起来可能像是一个花哨的数学术语，但不要被吓到。这仅仅意味着 Git 中的每个快照都引用一组“父快照”，即它之前的快照。它是一组父快照而不是单个父快照（如在线性历史中那样），因为一个快照可能来自多个父快照，例如，由于合并（合并）两个并行开发分支。

Git 将这些快照称为“提交”。可视化提交历史可能看起来像这样：

```plaintext
o <-- o <-- o <-- o
            ^
             \
              --- o <-- o
```

在上述 ASCII 艺术中， `o` 对应单个提交（快照）。箭头指向每个提交的父提交（这是一个“先于”关系，而不是“后于”）。在第三个提交之后，历史分支成两条独立的分支。这对应于，例如，两个独立开发并行进行的不同功能。未来，这些分支可能会合并，创建一个包含这两个功能的新快照，产生一个新的历史，如下所示，新创建的合并提交以粗体显示：

```

o <-- o <-- o <-- o <---- o
            ^            /
             \          v
              --- o <-- o
```

Git 中的提交是不可变的。但这并不意味着错误不能被纠正；只是对提交历史的“编辑”实际上是在创建全新的提交，并且引用（见下文）会被更新以指向新的提交。

## 数据模型，以伪代码形式

将 Git 的数据模型以伪代码形式写下来，或许会有所启发：

```plaintext
// a file is a bunch of bytes
type blob = array<byte>

// a directory contains named files and directories
type tree = map<string, tree | blob>

// a commit has parents, metadata, and the top-level tree
type commit = struct {
    parents: array<commit>
    author: string
    message: string
    snapshot: tree
}
```

这是一个干净、简单的历史模型。

## 对象和内容寻址

“对象”是一个 blob、树或提交：

```plaintext
type object = blob | tree | commit
```

在 Git 的数据存储中，所有对象都通过其 SHA-1 哈希进行内容寻址。

```plaintext
objects = map<string, object>

def store(object):
    id = sha1(object)
    objects[id] = object

def load(id):
    return objects[id]
```

blob、树和提交以这种方式统一：它们都是对象。当它们引用其他对象时，它们实际上不在其磁盘表示中包含它们，而是通过哈希值引用它们。

例如，上面示例目录结构的树（使用 `git cat-file -p 698281bc680d1995c5f4caaf3359721a5a58d48d` 可视化），看起来是这样的：

```plaintext
100644 blob 4448adbf7ecd394f42ae135bbeed9676e894af85    baz.txt
040000 tree c68d233a33c5c06e0340e4c224f0afca87c8ce87    foo
```

树本身包含指向其内容的指针， `baz.txt` （一个 blob）和 `foo` （一个树）。如果我们查看与 baz.txt 对应的哈希 `git cat-file -p 4448adbf7ecd394f42ae135bbeed9676e894af85` 所指向的内容，我们会得到以下信息：

```plaintext
git is wonderful
```

## 引用

现在，所有的快照都可以通过它们的 SHA-1 哈希来识别。这很麻烦，因为人类不擅长记住 40 个十六进制字符的字符串。

Git 对这个问题的解决方案是为 SHA-1 哈希提供人类可读的名称，称为“引用”。引用是指向提交的指针。与不可变对象不同，引用是可变的（可以更新以指向新的提交）。例如， `master` 引用通常指向开发主分支的最新提交。

```plaintext
references = map<string, string>

def update_reference(name, id):
    references[name] = id

def read_reference(name):
    return references[name]

def load_reference(name_or_id):
    if name_or_id in references:
        return load(references[name_or_id])
    else:
        return load(name_or_id)
```

通过这种方式，Git 可以使用人类可读的名称如“master”来指代历史中的特定快照，而不是一个长十六进制字符串。

有一个细节是我们通常需要一个“当前所在位置”的概念，这样当我们创建一个新的快照时，我们知道它是相对于什么（如何设置提交的 `parents` 字段）。在 Git 中，这个“当前所在位置”是一个特殊的引用，称为“HEAD”。

## 仓库

最后，我们可以定义 Git 仓库是什么（大致上）：它是数据 `objects` 和 `references` 。

在磁盘上，所有 Git 存储都是对象和引用：这就是 Git 的数据模型全部。所有 `git` 命令都映射到通过添加对象和添加/更新引用来对提交的有向无环图进行某种操作。

每当你输入任何命令时，都要思考这个命令对底层图数据结构做了什么操作。反过来，如果你试图对提交的有向无环图做出某种特定类型的改变，例如“丢弃未提交的更改并让‘master’引用指向提交 `5d83f9e` ”，那么很可能有一个命令可以做到这一点（例如，在这种情况下，是 `git checkout master; git reset --hard 5d83f9e` ）。

# 暂存区

这是一个与数据模型正交的概念，但它是一部分创建提交的接口。

一种你可以想象用来实现上述快照的方法是使用一个“创建快照”命令，该命令基于工作目录的当前状态创建一个新的快照。有些版本控制工具是这样工作的，但 Git 不是。我们想要干净的快照，并且从当前状态创建快照可能并不总是理想的。例如，想象一个场景，你已经实现了两个独立的功能，并且想要创建两个独立的提交，第一个提交引入第一个功能，下一个提交引入第二个功能。或者想象一个场景，你在代码中到处添加了用于调试的打印语句，并且还有一个 bug 修复；你想要提交 bug 修复，同时丢弃所有的打印语句。

Git 通过一种称为“暂存区”的机制来适应这些场景，允许你指定哪些修改应该包含在下一个快照中。

# Git 命令行界面

为了避免重复信息，我们不会在这些讲义中详细解释下面的命令。请参阅强烈推荐的《Pro Git》获取更多信息，或者观看讲座视频。

## 基础

- `git help <command>` : 获取 git 命令的帮助
- `git init` : 创建一个新的 git 仓库，数据存储在 `.git` 目录中
- `git status` : 告诉你正在发生什么
- `git add <filename>` : 将文件添加到暂存区
- `git commit` : 创建一个新的提交
  - 写好提交信息！
  - 写好提交信息的更多理由！
- `git log` : 显示扁平化的历史记录
- `git log --all --graph --decorate` : 将历史记录可视化为有向无环图
- `git diff <filename>` : 显示与暂存区相比所做的更改
- `git diff <revision> <filename>` : 显示文件在不同快照之间的差异
- `git checkout <revision>` : 更新 HEAD（如果切换分支，则同时更新当前分支）

## 分支与合并

- `git branch` : 显示分支
- `git branch <name>` : 创建分支
- `git switch <name>` : 切换到分支
- `git checkout -b <name>` : 创建分支并切换到它
  - 与 `git branch <name>; git switch <name> 相同`
- `git merge <revision>` : 合并到当前分支
- `git mergetool` : 使用一个花哨的工具来帮助解决合并冲突
- `git rebase` : 将一组补丁重新应用到新的基础之上

## 远程仓库

- `git remote` : 列出远程仓库
- `git remote add <name> <url>` : 添加远程仓库
- `git push <remote> <local branch>:<remote branch>` : 将对象发送到远程仓库，并更新远程引用
- `git branch --set-upstream-to=<remote>/<remote branch>` : 设置本地分支和远程分支之间的对应关系
- `git fetch` : 从远程检索对象/引用
- `git pull` : 与 `git fetch; git merge 相同`
- `git clone` : 从远程下载仓库

## 撤销

- `git commit --amend` : 编辑提交的内容/信息
- `git reset <file>` : 取消暂存文件
- `git restore` : 放弃更改

# 高级 Git

- `git config` : Git 非常可定制
- `git clone --depth=1` : 浅克隆，不包含完整版本历史
- `git add -p` : 交互式暂存
- `git rebase -i` : 交互式变基
- `git blame` : 显示最后编辑了哪一行
- `git stash` : 暂时移除工作目录中的修改
- `git bisect` : 二分搜索历史记录（例如用于回归测试）
- `git revert` : 创建一个新的提交，以撤销先前提交的效果
- `git worktree` : 同时检出多个分支
- `.gitignore` : 指定要忽略的未跟踪文件

# 杂项

- 图形界面：Git 有很多图形界面客户端。我们个人不使用它们，而是使用命令行界面。
- Shell 集成：将 Git 状态作为 shell 提示符的一部分（zsh、bash）非常方便。通常包含在 Oh My Zsh 等框架中。
- 编辑器集成：与上述类似，具有许多便捷的功能集成。fugitive.vim 是 Vim 的标准集成。
- 工作流程：我们教了你数据模型和一些基本命令；我们没有告诉你在大项目上工作时应该遵循哪些实践（而且有很多不同的方法）。
- GitHub：Git 不是 GitHub。GitHub 有一种特定的方式来为其他项目贡献代码，称为拉取请求。
- 其他 Git 提供商：GitHub 并不特殊：有很多 Git 仓库托管服务，比如 GitLab 和 BitBucket。

# 练习

1. 如果你以前没有 Git 的使用经验，可以尝试阅读《Pro Git》的前几章，或者通过 Learn Git Branching 这样的教程来学习。在学习过程中，将 Git 命令与数据模型联系起来。
2. 克隆课程网站的仓库。
  1. 通过将版本历史可视化成图来探索。
  2. 最后一个修改 `README.md` 的人是谁？（提示：使用 `git log` 带参数）。
  3. 与 `_config.yml` 中 `collections:` 行最后一次修改相关联的提交信息是什么？（提示：使用 `git blame` 和 `git show` ）。
3. 学习 Git 时常见的错误之一是提交不应由 Git 管理的大文件或添加敏感信息。尝试将文件添加到仓库中，进行一些提交，然后从历史记录中删除该文件（不只是最新提交）。你可能需要看看这个。
4. 从 GitHub 克隆一个仓库，并修改其中一个现有文件。当你执行 `git stash` 时会发生什么？运行 `git log --all --oneline` 时你会看到什么？执行 `git stash pop` 来撤销你用 `git stash` 做的修改。在什么情况下这可能很有用？
5. 像许多命令行工具一样，Git 提供了一个名为 `~/.gitconfig` 的配置文件（或点文件）。在 `~/.gitconfig` 中创建一个别名，这样当你运行 `git graph` 时，你会得到 `git log --all --graph --decorate --oneline` 的输出。你可以通过直接编辑 `~/.gitconfig` 文件来实现这一点，或者你可以使用 `git config` 命令来添加别名。有关 git 别名的信息可以在这里找到。
6. 在运行 `git config --global core.excludesfile ~/.gitignore_global` 后，你可以在 `~/.gitignore_global` 中定义全局忽略模式。这会设置 Git 将使用的全局忽略文件的位置，但你仍然需要手动在该路径下创建该文件。设置你的全局 gitignore 文件以忽略特定于操作系统或编辑器的临时文件，例如 `.DS_Store` 。
7. 为本课程网站仓库创建分支，找到一个拼写错误或其他可以改进的地方，并在 GitHub 上提交一个拉取请求（你可能需要参考这个）。请只提交有用的 PR（不要给我们发送垃圾信息，请！）如果你找不到可以改进的地方，可以跳过这个练习。
8. 通过模拟协作场景来练习解决合并冲突：
  1. 创建一个新仓库，命名为 `git init` ，并创建一个名为 `recipe.txt` 的文件，包含几行内容（例如，一个简单的食谱）。
  2. 提交它，然后创建两个分支： `git branch salty` 和 `git branch sweet` 。
  3. 在 `salty` 分支中，修改一行（例如，将“1 杯糖”改为“1 杯盐”），然后提交。
  4. 在 `sweet` 分支中，以不同的方式修改同一行（例如，将“1 杯糖”改为“2 杯糖”），然后提交。
  5. 现在切换到 `master` 并尝试 `git merge salty` ，然后 `git merge sweet` 。会发生什么？查看 `recipe.txt` 的内容—— `<<<<<<<` 、 `=======` 和 `>>>>>>>` 标记代表什么？
  6. 通过编辑文件保留你想要的内容，删除冲突标记，并使用 `git add` 和 `git commit` （或 `git merge --continue` ）完成合并来解决冲突。或者，尝试使用 `git mergetool` 和图形界面或基于终端的合并工具来解决冲突。
  7. 使用 `git log --graph --oneline` 可视化你刚刚创建的合并历史。
